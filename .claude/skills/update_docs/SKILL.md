# Skill: Update the documentation

Use this skill whenever a change touches behaviour, a path, a command, a rule or a skill. The docs ship in
the same PR as the code (RULE-79) and are held to the tree by `docs_check` (CI Gate 5).

**Contract:** [`CONTRIBUTING.md` § 5](../../../CONTRIBUTING.md#5-documentation-contract) — read it.
**Rules** ([registry](../../../docs/en/reference/01_rules.md)): RULE-79, and the id of any rule you cite. Cite them;
do not restate them.

## The contract in six lines

1. **The code is the source of truth**, then the registry, then `docs/en/**`, then `CLAUDE.md` / `.agents/AGENTS.md` /
   `.claude/skills/`, then `README.md`, then `docs/vi/**`. When two disagree the lower one is the one to fix.
2. **Verify every statement against the tree**: each path exists, each class, method and signature is grep-able, each
   command was run or its source read, each code sample is **copied from a real file** (never written from memory),
   each exit code and behaviour claim is read from the implementation. Never document an intention.
3. **State a rule once** — in the registry — and cite `RULE-NN` with a link everywhere else, keeping the
   guide-specific *how* and dropping the restated *what*. Prefer deleting a duplicated explanation over syncing it.
4. **Numbers are re-measured, not copied.** Counts of rules, packages, checks and catalog rows may be stated only if
   a command or test asserts them; never test counts, line counts, durations, commit shas, coverage or machine paths.
5. **History is not guidance**: how the repo got here belongs in `docs/history/` (English only, outside the parity check).
6. **`docs/vi/**` mirrors `docs/en/**` 1:1.**

## Steps

### Step 1: Find every place that says it

```bash
grep -rn "<symbol or path or command>" --include=*.md . | grep -v node_modules
```

Look in `docs/en/` (`architecture/`, `getting-started/`, `guides/`, `operations/`, `reference/`), the `docs/vi/` twin,
`README.md` / `README.vi.md`, `tools/README.md` / `tools/README.vi.md`, a package's `README.md` / `README.vi.md`,
`CLAUDE.md`, `.agents/AGENTS.md`, `.claude/skills/*/SKILL.md`, `CONTRIBUTING.md`, `.github/workflows/README.md` and an
app's hand-written `README.md` (outside its generated `report` region). Fix what is wrong, delete what describes
removed code, add what is missing.

### Step 2: A new or changed rule — the registry first

In [`docs/en/reference/01_rules.md`](../../../docs/en/reference/01_rules.md) § *Adding or changing a rule*:

1. Add a row in the matching range with the **next free id** — never renumber, never reuse; a retired rule keeps its row,
   marked retired.
2. Name what enforces it (`arch_check Rn`, `analyzer (<lint>)`, `test (<file>)`, `CI gate N`, `composer verify`,
   `docs_check`, or `review`). If nothing mechanical does, write `review` — do not imply a gate that does not exist; when
   a rule becomes machine-checked, update **Enforced by** in the same PR.
3. Put the why, the exceptions and the history in the section below or in the right guide and link it from **Details**.
4. Mirror the row in `docs/vi/reference/01_rules.md`. If the rule is among the most violated, add its one-liner to the
   top-rules table of `CLAUDE.md` — as an id and one line, not a paraphrase (`.agents/AGENTS.md` holds no rules; it points at `CLAUDE.md`).

`docs_check` fails on a `RULE-NN` the registry does not define, a duplicate id, or a vi registry whose ids differ.

### Step 3: Edit the English file, then its Vietnamese twin in the same pass

Same filenames, the **same number of headings per level, fenced code blocks and table rows**, the same `RULE-NN` ids.
Comments inside a code block may be translated; identifiers, commands, paths and technical terms stay English; the
Vietnamese must read naturally, not word for word. The pairs are every `docs/en/**.md` ↔ `docs/vi/**.md`,
`README.md` ↔ `README.vi.md`, and `<name>.md` ↔ `<name>.vi.md` beside `tools/README.md`, `tools/code_review/README.md` and
the package READMEs that have one. Single-language: `CLAUDE.md`, `CONTRIBUTING.md`, `CHANGELOG.md`, `SECURITY.md`,
`.agents/AGENTS.md`, the skills, `.github/**` and the apps' READMEs.

Never edit a generated region: an app README's `report` region is regenerated by `composer sync` (RULE-16); a barrel's
exports by the barrel generator (RULE-75).

### Step 4: Run docs_check

```bash
dart tools/docs_check/check.dart                 # Gate 5: paths, links, en <-> vi parity, RULE ids; exit 1 on a finding
dart tools/docs_check/check.dart --verbose       # adds an allowlist block and every removed-sample reference
```

- A backticked span that begins with a real top-level directory, and every Markdown link (resolved relative to its file),
  must exist; a span with a `<placeholder>` segment is a template, so only the part before the first placeholder must
  exist. A dead reference inside a sample bundle removed by `remove_sample` is INFO, not a failure.
- A path that is correctly absent goes in `tools/docs_check/allowlist.txt`, one per line with a `#` reason, and only for
  generated files, secrets, or tutorial/placeholder paths — never to silence a typo.
- An intentional en ↔ vi difference goes in `tools/docs_check/parity_allowlist.txt` as `<english file> <metric or *>  # reason`;
  a difference almost always means a section, command or table row was added to one language and never reached the other —
  translate it across instead.
- Exit `0` clean, `1` a dead reference / parity mismatch / RULE-id problem, `64` an unknown argument. When you change
  `docs_check` itself, add the case to `tools/test/` (RULE-64).

### Step 5: Stamp the translation

Commit the English change first, then stamp each Vietnamese file you synced — the stamp records the English commit it was
translated from:

```bash
dart tools/docs_check/check.dart --stamp-translations docs/vi/<file>.md
dart tools/docs_check/check.dart --stale-translations      # lists docs/vi files behind their English source (advisory, exit 0)
```

Stamp only files you actually synced: with no file argument the command stamps **every** `docs/vi` file and marks them
all current, which is for adopting stamps, not for a routine change. Never write a stamp by hand or copy a sha.

### Step 6: CHANGELOG and commit

A user-visible change gets one line under `## [Unreleased]` in `CHANGELOG.md`, in `Added`, `Changed`, `Removed` or
`Fixed` (Keep a Changelog). Commit with Conventional Commits — `docs(<scope>): <summary>`, lowercase, no trailing
period, a body that says why.

```bash
dart tools/docs_check/check.dart                          # Gate 5, zero findings
dart tools/docs_check/check.dart --stale-translations     # the pairs you touched are not listed
dart tools/arch_check/check.dart                          # when the docs name a rule's enforcement, it still holds
cd tools && dart test                                     # after any change to docs_check itself
```
