# `apps/admin` — the second app

A back-office app built from the **same modules** as `apps/mobile`, composing a different
subset of them: `auth` and `settings`, and none of `dashboard`, `splash`, `onboarding` or
`home`. It exists to keep the composition design honest. Every optional lookup in
`platform_app_shell` (`getItOrNull`, `getAllOrEmpty`) has a missing contribution in this app,
permanently, instead of only in a thought experiment:

| Not composed | What the shell does instead |
|:--|:--|
| `feature_splash` (`IAppSplashScreen`) | keeps the native splash through boot |
| `feature_onboarding` (`IAppEntryLocation`) | starts on the first destination and goes straight to the login check |
| `feature_home` (`HomeNavigator`) | after sign-in, goes to `AppRouter.fallbackLocation` — the settings tab |
| `feature_dashboard` (`DashboardRouteModule`) | renders the destinations without chrome |
| `core_notifications` + Firebase | nothing: no `notifications` DI group, no `lib/firebase/` |

Two of those rows were bugs until this app was planned — a first launch without onboarding
skipped the login redirect, and a sign-in without home stayed on the login screen. A third,
the blank screen without a dashboard, was found while writing it.

## What is in here

```
apps/admin/
├── app_manifest.yaml      which modules, which DI group order — the only file you edit to change the app
├── pubspec.yaml           path dependencies generated between composer markers
├── env.dev                --dart-define values (no secrets; env.prod is yours to create)
└── lib/
    ├── main.dart          runShellApp(configureDependencies: configureDependencies)
    └── di/
        ├── injection.dart generated by composer
        └── di.dart        barrel
```

That is the whole app. The boot sequence, router, storage adapters and material wrapper come from
[`platform/app_shell`](../../platform/app_shell/).

To change what it is made of, edit `app_manifest.yaml`, then from the repository root:

```bash
dart tools/composer/composer.dart sync --app admin
flutter pub get
dart run build_runner build -d --workspace
```

## Running it

No platform runner folders are committed yet — the app is meant for desktop, and which desktop
platforms a team ships is its own decision. Generate them once, from this directory:

```bash
cd apps/admin
flutter create --platforms=macos,windows,linux --org com.example --project-name admin_app .
```

`flutter create` leaves existing files alone and adds what is missing. It also writes a
`test/widget_test.dart` for a counter app that does not exist here — delete it.

Then, still from `apps/admin/`:

```bash
flutter run -d macos --dart-define-from-file=env.dev
```

Notes that apply to this app specifically:

- **Why desktop, not web.** `data_core` opens its SQLite cache through `core_database`, which uses
  `drift/native` — FFI, so it does not compile for the web. `drift/native` also needs a SQLite
  library at runtime; check the `sqlite3` package's notes for the desktop platform you pick.
- **Flavor.** `AppConfig.appFlavor` reads the flavor the app was built with and falls back to
  `dev` when there is none, so a plain `flutter run` registers the `dev` DI environment.
- **Branding.** `tools/theme_generator/theme_setting.dart` takes `--app admin`, but runs
  `flutter_native_splash` and `icons_launcher` from this directory, so both must first be added
  to this app's `dev_dependencies` — and the shared configs at the repository root only target
  mobile platforms today. This app does not use Firebase.

## What checks it today

`composer verify` (CI Gate 0) regenerates this app's composition and fails on drift, and
`arch_check` R10 fails if anything under `lib/` other than `injection.dart` imports a module.
Nothing in CI builds it yet.
