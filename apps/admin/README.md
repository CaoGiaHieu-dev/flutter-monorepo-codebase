# `apps/admin` — the second app

A back-office app built from the **same modules** as `apps/mobile`, composing a different
subset of them: `auth` and `settings`, and none of `dashboard`, `splash`, `onboarding`,
`home` or `cache`. It exists to keep the composition design honest. Every optional lookup in
`platform_app_shell` (`getItOrNull`, `getAllOrEmpty`) has a missing contribution in this app,
permanently, instead of only in a thought experiment — the report below says which, and why.

## How to read this app

1. **The report below** — generated from the manifest: identity and flavors, the platforms and what
   each enables, the composition in boot order, what the shell resolves from this app (required vs
   optional, and why anything is absent), and the decisions to revisit before shipping.
2. [`app_manifest.yaml`](app_manifest.yaml) — what you *declare*: name, flavors, environment keys,
   platforms, capabilities, DI groups, modules.
3. [`lib/app/app_profile.dart`](lib/app/app_profile.dart) — the manifest as const Dart (a generated
   `facts` region) and `appProfile`, how the shell behaves for this app.
4. [`lib/app/app_hooks.dart`](lib/app/app_hooks.dart) — code the app runs at fixed points of the boot.

```bash
dart tools/composer/composer.dart describe --app admin   # the report below, on stdout
dart tools/composer/composer.dart sync --app admin       # regenerate everything generated from the manifest
dart tools/composer/composer.dart verify                 # CI Gate 0: fails when any of it has drifted
```

Native notes (not checked):
- **web** — The flavor comes from --dart-define=APP_FLAVOR=<flavor> (the web has no --flavor). Secure storage needs a secure context (https or localhost); the browser owns TLS, so nothing is pinned. Without a splash module the page stays empty until boot ends. An app that links core_database needs sqlite3.wasm and drift_worker.js in its web runner, which `composer runners` writes. Measured.
- **windows** — flutter_secure_storage needs Visual Studio 2022 "Desktop development with C++" with the ATL component. Linking core_notifications downloads the Firebase C++ SDK (FlutterFire). The window title is the package name until the runner is ejected. Unverified.

## Running it

No runner is committed: all four platforms are `runner: scaffold`, generated by `composer runners`
and ignored by git through the `runners` region of `.gitignore` (RULE-83). `configure.dart` writes
them; to regenerate them — after a Flutter upgrade, with `--force` — run, from the repository root:

```bash
dart tools/composer/composer.dart runners --app admin
```

A generated runner has no native flavors, so every run names the flavor with
`--dart-define=APP_FLAVOR=dev`. From `apps/admin/`:

```bash
flutter run -d chrome --web-port 5310 --dart-define-from-file=env.dev --dart-define=APP_FLAVOR=dev
flutter run -d linux --dart-define-from-file=env.dev --dart-define=APP_FLAVOR=dev    # or macos, windows
```

The fixed web port keeps the browser's storage between runs (it belongs to the origin, port
included); `.vscode/launch.json` has *Admin (Web, Dev)* and *Admin (Desktop, Dev)* with the same flags.
The boot test is what CI runs for each platform:

```bash
flutter test integration_test/boot_test.dart -d linux --dart-define-from-file=env.dev --dart-define=APP_FLAVOR=dev
flutter drive --driver=test_driver/integration_test.dart --target=integration_test/boot_test.dart \
  -d web-server --browser-name=chrome --headless --chrome-binary=<chrome> \
  --dart-define-from-file=env.dev --dart-define=APP_FLAVOR=dev
```

The web boot needs a chromedriver of the same build as that Chrome on port 4444; Linux needs a
display and a Secret Service. To own a runner — a window title, an icon, a URL scheme, PWA
metadata — eject it (`runner: committed`, `composer sync`, commit the folder):
[`docs/en/guides/13_app_composition.md`](../../docs/en/guides/13_app_composition.md) § 7.

Notes that apply to this app specifically:

- **The web and the desktop, proven by the boot test.** `integration_test/boot_test.dart` reaches
  its first drawn screen in headless Chrome and on Linux (with an unlocked keyring and with no
  Secret Service) on every pull request, and on macOS and Windows in `platforms_full.yml`. Secure
  storage on the web needs a secure context (`https` or `localhost`). On the web the browser owns
  TLS, so `AppInitializer` installs no `HttpOverrides` and there is no SSL pinning. On Windows,
  macOS and Linux the manifest's pin decision applies (the plugin sees the leaf certificate only);
  see [`docs/en/guides/08_networking.md`](../../docs/en/guides/08_networking.md) § 10. On Linux
  the derived `secure_storage: memory_fallback` keeps secure values in memory when the session runs
  no Secret Service. This app opens no database: it composes neither the `cache` module nor
  `core_database`, so no Drift or SQLite code is in its dependency graph. The platform status of
  both apps: [`docs/en/architecture/02_core.md`](../../docs/en/architecture/02_core.md) § 11.
- **Flavor.** `AppConfig.appFlavor` reads the flavor the build declared — here always through
  `--dart-define=APP_FLAVOR=<flavor>`, since no runner of this app has native flavors. With none,
  it falls back by build mode: `dev` in a **debug** build, so a plain `flutter run` registers the
  `dev` DI environment, and `prod` in a profile or release build. TLS is stricter still:
  certificate validation is bypassed only in a debug build that *declared* `dev`
  (`APP_FLAVOR=dev`), so a build with no flavor keeps validation on (and, on the desktop, logs an ERROR; on the web the browser validates certificates) even when
  its DI environment is `dev`.
- **Branding.** `tools/theme_generator/theme_setting.dart --app admin` is refused. The tool checks
  every precondition before writing anything, and requires the app to have both `android/` and
  `ios/` — the shared `flutter_native_splash` / `icons_launcher` configs at the repository root
  enable both — as well as both packages in its `dev_dependencies`. This app declares neither
  platform, so adding the `dev_dependencies` alone does not unblock it. This app does not use
  Firebase.

## What checks it today

`composer verify` (CI Gate 0) regenerates this app's composition, facts, report and `.gitignore`
region and fails on drift — and refuses a manifest whose declaration is incomplete — and
`arch_check` R10 fails if any Dart file of the app other than `lib/di/injection.dart` imports a module.
CI Gate 3 runs `test/di_smoke_test.dart`, which boots this app's real DI graph on each desktop
platform for every flavor and builds every `@injectable` factory — so a missing registration or a
DI ordering mistake in this composition fails the PR. The `platforms` job of
`pr_quality_check.yml` generates the web and Linux runners and runs the boot test on both;
`platforms_full.yml` does the same on macOS and Windows, and builds the web in release and Wasm mode.
