# `apps/admin` — the second app

A back-office app built from the **same modules** as `apps/mobile`, composing a different
subset of them: `auth` and `settings`, and none of `dashboard`, `splash`, `onboarding`,
`home` or `cache`. It exists to keep the composition design honest. Every optional lookup in
`platform_app_shell` (`getItOrNull`, `getAllOrEmpty`) has a missing contribution in this app,
permanently, instead of only in a thought experiment — the report below says which, and why.

## How to read this app

1. **The report below** — generated from the manifest: identity and flavors, the platforms and what
   each enables, the composition in boot order, what the shell resolves from this app (required vs
   optional, and why anything is absent), and the decisions to revisit before shipping.
2. [`app_manifest.yaml`](app_manifest.yaml) — what you *declare*: name, flavors, environment keys,
   platforms, capabilities, DI groups, modules.
3. [`lib/app/app_profile.dart`](lib/app/app_profile.dart) — the manifest as const Dart (a generated
   `facts` region) and `appProfile`, how the shell behaves for this app.
4. [`lib/app/app_hooks.dart`](lib/app/app_hooks.dart) — code the app runs at fixed points of the boot.

No platform runner folders are committed yet — the manifest declares `windows`, `macos`, `linux`
and `web` with `runner: scaffold`, and which of them a team ships is its own decision. Generate
the ones you ship once, from this directory (the report above prints the line for all four):

```bash

```

Then flip that platform to `runner: committed` in `app_manifest.yaml` and run `composer sync`:

- `analysis_options.yaml`, whose `flutter_lints` include replaces the repository-root analysis
  options for everything under `apps/admin/`.

```bash

```

Then, still from `apps/admin/`:

```bash

```

Notes that apply to this app specifically:

- **Desktop first; the web works too.** This app has been built for the web and loaded in a
  browser: after `flutter create --platforms=web .` it builds with `flutter build web` and boots
  to the sign-in screen, with secure storage and preferences working (the page must be a secure
  context: `https` or `localhost`). On the web the browser owns TLS, so `AppInitializer` installs
  no `HttpOverrides` and there is no SSL pinning. The measurement and what `apps/mobile` still
  lacks on the web are in [`docs/en/architecture/02_core.md`](../../docs/en/architecture/02_core.md)
  § 11. This app opens no database: it composes neither the `cache` module nor `core_database`,
  so no Drift or SQLite code is in its dependency graph.
- **Flavor.** `AppConfig.appFlavor` reads the flavor the app was built with. With none, it falls
  back by build mode: `dev` in a **debug** build, so a plain `flutter run` registers the `dev` DI
  environment, and `prod` in a profile or release build. TLS is stricter still: certificate
  validation is bypassed only in a debug build that *declared* `--flavor dev`, so a build with no
  flavor keeps validation on (and logs an ERROR) even when its DI environment is `dev`.
- **Branding.** `tools/theme_generator/theme_setting.dart --app admin` is refused. The tool checks
  every precondition before writing anything, and requires the app to have both `android/` and
  `ios/` — the shared `flutter_native_splash` / `icons_launcher` configs at the repository root
  enable both — as well as both packages in its `dev_dependencies`. This app has neither platform
  directory, so adding the `dev_dependencies` alone does not unblock it; it stays refused until
  the app gains `android/` and `ios/`. This app does not use Firebase.

## What checks it today

`composer verify` (CI Gate 0) regenerates this app's composition, facts and report and fails on
drift — and refuses a manifest whose declaration is incomplete — and
`arch_check` R10 fails if any Dart file of the app other than `lib/di/injection.dart` imports a module.
CI Gate 3 runs `test/di_smoke_test.dart`, which boots this app's real DI graph for every flavor and
builds every `@injectable` factory — so a missing registration or a DI ordering mistake in this
composition fails the PR. What CI does
not do is build a binary of it: the build job builds `apps/mobile` only.
