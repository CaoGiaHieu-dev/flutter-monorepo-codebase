# `apps/mobile` — the sample app

The phone/tablet app that composes **every sample module** in the workspace. It is the reference
composition: each routing contract, DI group and fallback the shell supports has a real
contributor here. [`apps/admin`](../admin/README.md) composes the same shell with only `auth` and
`settings`.

## How to read this app

1. **The report below** — generated from the manifest: identity and flavors, the platforms and what
   each enables, the composition in boot order, what the shell resolves from this app (required vs
   optional, and why anything is absent), and the decisions to revisit before shipping.
2. [`app_manifest.yaml`](app_manifest.yaml) — what you *declare*: name, flavors, environment keys,
   platforms, capabilities, DI groups, modules.
3. [`lib/app/app_profile.dart`](lib/app/app_profile.dart) — the manifest as const Dart (a generated
   `facts` region) and `appProfile`, how the shell behaves for this app.
4. [`lib/app/app_hooks.dart`](lib/app/app_hooks.dart) — code the app runs at fixed points of the boot.

```bash
dart tools/composer/composer.dart describe --app mobile   # the report below, on stdout
dart tools/composer/composer.dart sync --app mobile       # regenerate everything generated from the manifest
dart tools/composer/composer.dart verify                  # CI Gate 0: fails when any of it has drifted
```

### 3. Composition, in boot order (a)
| # | Group (phase) | Packages | Why |
|:-:|:--|:--|:--|
| 1 | core (before) | core_common, core_network, core_storage, core_database, core_di | mechanism only, registered before anything the app or a module adds. core_database registers nothing: each package that persists data declares its own database |
| 2 | notifications (after) | core_notifications | PushNotificationService is eager and injects FirebaseOptions, which lib/firebase/ registers between the two phases — it cannot sit in core. An app without push drops this group |
| 3 | shell (after) | platform_shell_adapters, platform_app_shell | adapters first (storage adapters, AppBootStorage, NetworkConfig), then router and deep links. ui injects the storage adapters, so shell precedes it |
| 4 | ui (after) | core_base_ui | ThemeProvider and LanguageProvider inject IThemeStorage / ILanguageStorage, which shell registers. They are lazy, so only an eager singleton added here would fail on another order (RULE-13); composer verify holds the order (V16) |
| 5 | domain (after) | domain_core, domain_auth, domain_cache | pure-Dart use cases and repository interfaces: data implements them and features inject them, so domain comes first of the three |
| 6 | data (after) | data_core, data_auth, data_cache | a module that opens a database with @preResolve runs the migrations contributed before it, so contributors precede it |
| 7 | feature (after) | feature_auth, feature_home, feature_settings, feature_onboarding, feature_splash, feature_dashboard | screens, routes and controllers inject the use cases the domain and data groups register, so features come after both |
| 8 | other (after) | provider_state_management, bloc_state_management | no ordering constraint: the state-management bases register nothing, so they go last by convention |

Modules: auth (api, domain, data, feature) · home (api, feature) · settings (feature) · onboarding (feature) · splash (feature) · dashboard (feature) · cache (domain, data).

**This app must provide:**
- `FirebaseOptions` for `core_notifications`: one registration per flavor (dev, staging, prod). apps/mobile/lib/firebase/firebase_module.dart, written by dart tools/firebase/firebase_config.dart. Native, not checked: google-services.json per Android flavor; aps-environment on iOS.

The DI smoke test boots every flavor, so a missing registration fails it with "<Type> is not registered".

### 7. Extension points (e)
Channels: manifest sections (`platforms`, `capabilities`, `flavors`, `env`, `di_groups`, `modules`) · the profile (`lib/app/app_profile.dart`) · hooks (`lib/app/app_hooks.dart`, type `const ShellHooks(`: the error channels, `beforeDependencies`, `afterBoot`, `navigatorObservers`, `redirect`, `configureWindow`) · contracts the app registers under `lib/app/`.

**Locked** — changing one means editing the shared package, for every app: the shadow and scrim colours, breakpoints, component themes, page transitions, the default interceptor chain, the 404 page, push channel and icon, deep-link allow-lists, logger limits, system UI overlay, secure-storage options. Replacing a shell-owned type by registration order is unsupported: the first registration of a type wins (GetIt, `enableRegisteringMultipleInstancesOfOneType`), which works only for types registered in the `after` groups.

## First run

From the repository root, set up the workspace once:

```bash
dart tools/workspace_setup/configure.dart
```

The app then needs files that are **gitignored** and absent from a fresh clone:

- `lib/firebase/firebase_options_dev.dart`, `_staging.dart` and `_prod.dart`. All three are
  imported unconditionally, so nothing compiles without them.
- `android/app/src/<flavor>/google-services.json` for each flavor you build on Android.

Create them with `dart tools/firebase/firebase_config.dart --app mobile`, which needs the Firebase
CLI installed and logged in. If you have no Firebase project, run
`dart tools/workspace_setup/configure.dart --stub-firebase` instead: it writes compile-only stubs and
leaves any file that already exists alone. With stubs the app builds, but push notifications and other Firebase features do not work. Both
paths are in [`01_setup.md` § 3](../../docs/en/getting-started/01_setup.md).

## Running and building

Always from **this directory**. The workspace root has no `android/` or `ios/` project.

```bash
cd apps/mobile
flutter run --flavor dev --dart-define-from-file=env.dev
flutter build apk --flavor dev --debug --dart-define-from-file=env.dev
```

| Flavor | Env file |
|:--|:--|
| `dev` | `env.dev` (committed) |
| `staging` | `env.stg` (committed) |
| `prod` | `env.prod`: **create it yourself**, it is gitignored |

The application and bundle ID of each flavor are in section 1 above (read from the native projects).
`env.prod` takes the same keys as `env.dev`: `BASE_URL`, `WEB_DOMAIN`, `APP_LINK_MODE`, `APP_NAME`.
VS Code users can pick **App (Dev)**, **App (Staging)** or **App (Prod)** from `.vscode/launch.json`.

## Signing

`android/key-dev.properties` and `android/keystore-dev.jks` are **committed on purpose**, so a
fresh clone builds and runs `dev` with no setup. Staging and prod read `key-stg.properties` and
`key.properties`. If either file is absent, debug and profile builds of that flavor fall back to the
dev key, so a fresh clone runs every flavor; a `--release` build of staging or prod **fails** instead
(staging has an opt-in escape hatch, prod has none). Never ship a production release with the dev
keystore: it is public. Creating a release key, and the check to run before a prod build, are in
[`02_fastlane_release.md` § 4](../../docs/en/operations/02_fastlane_release.md).
