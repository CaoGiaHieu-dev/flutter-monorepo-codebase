# 01. Core Infrastructure Layer

In the **Micro-packages Monorepo** architecture, the Core layer is no longer a monolithic directory but is divided into multiple independent specialized micro-packages located under the `packages/core/` directory. This design optimizes the separation of responsibilities, isolates errors, and accelerates source code compilation time.

---

## 🏛️ 1. Micro-Cores Organizational Map

The Core packages are designed independently and only interact with each other downwards to avoid circular dependency errors:

```text
packages/core/
├── common/             # [Pinnacle Core] System constants, Base Routes, Enums, Errors
├── di/                 # [DI Hub] Relay station for Interface Navigators, Routing Modules
├── base_ui/            # [Design System] Themes, TextStyles, Assets (Fonts, Images, Icons), Global UI Components
├── provider_state_management/   # [State Engine] BaseProvider, ViewStateModel, executeOperation helper
├── bloc_state_management/       # [State Engine] BaseBloc, BaseCubit, ViewState (Freezed) for BLoC architecture
├── storage/            # [Security Cache] Hardened Secure Storage, Reactive Storage Values, SharedPreferences
├── database/           # [Local DB] Drift + SQLite on background isolate for relational data
├── network/            # [Network Client] ApiClient (Dio Factory), Retrofit helper, Interceptors
└── notifications/      # [Push Service] Global push notification manager
```

## 📂 2. Detailed Survey of Each Micro-core Package

### A. Core Common (`packages/core/common`)
Acts as the connective nucleus and common definition for the entire system:
- **Constants & Enums**: Where environment configurations, local storage keys, API endpoints, and shared enums are defined.
- **Utils & Helpers**: Utility functions for string manipulation, date formatting, logic checks, etc.

### B. Core DI (`packages/core/di`)
This is the core communication "Hub" to resolve Circular Dependencies:
- **Decentralized Navigator Interfaces**: Contains Navigator Interfaces (`AuthNavigator`, `HomeNavigator`, `SettingsNavigator`, …) allowing Features to call each other without directly importing each other's source code.
- **Routing contribution contracts**: `IFeatureRouteModule` (stack routes, no order), `IDashboardTabModule` (bottom-nav tabs with order), `IAppEntryLocation` (cold start), `DashboardRouteModule` (dashboard chrome only), plus `NavigatorKeys`.
- Host helpers live in `core_common`: `getItOrNull`, `getAll`, `getAllOrEmpty`.

### C. Core Base UI (`packages/core/base_ui`)
Is the physical **Design System** of the application:
- **Themes & Colors**: Expanded light/dark mode configuration (`ThemeMode`, `AppTheme`).
- **Assets Catalog**: Safe wrapper for shared Fonts, Images, Icons.
- **Design Tokens**: Assets catalog, Fonts, Images, Icons, and translation language files (L10n). Contains 0 Flutter widgets.

### C. Core Network (`packages/core/network`)
API and network connection infrastructure:
- **`ApiClient`**: Factory that creates Dio Clients as requested by each package.
- **Security Interceptors**: 
  - `AuthInterceptor`: Automatically injects Bearer JWT Token from Secure Storage into the Header.
  - `LoggingInterceptor`: Outputs intuitive JSON HTTP logs via `dynamic_logger`.
  - `RetryInterceptor` & `RetryHandler`: **Global Retry Queue** mechanism. When multiple API call threads drop connection simultaneously, the system will temporarily pause (block) the entire queue, group them, and call the UI Dialog display function only once. If the user selects "Retry", the system automatically reruns all stuck requests.
- **Dependency Inversion via `NetworkConfig`**: Because the Network package is not allowed to directly import Storage modules (to get the Token) or UI (to show Retry Dialog), this package declares an open interface `NetworkConfig`. The Host App package (`app`) will write a `NetworkConfigImpl` class providing the parameters (Storage Token, AppDialogController) and pass it back into `core_network` via Dependency Injection. (Note: To avoid `build_runner` reporting fake missing dependency errors, the network module is configured with `ignoreUnregisteredTypes: [NetworkConfig]` at `@InjectableInit`).

### D. Core Storage (`packages/core/storage`)
High-end secure storage system:
- **AES-256 encryption**: Automatically software-encrypts with random IV for each record.
- **Hardware security**: Saves Master Key and encrypted data into Apple Keychain / Android KeyStore.
- **Reactive Values**: Stored values act as a Listener, automatically notifying and synchronizing with the interface when writing data.

### E. Core Database (`packages/core/database`)
Relational local database built on Drift:
- **Background isolate**: `NativeDatabase.createInBackground` keeps sqlite3 I/O off the UI thread.
- **Type-safe queries**: Tables, DAOs, and migrations generated by `drift_dev`.
- **Data layer ready**: `AppDatabase` is registered via `@preResolve` DI; see [14. Database System](./14_database_system.md).

### F. Core State Management (`packages/core/provider_state_management`)
UI logic and interface state synchronization backbone:
- **`BaseProvider`**: Base class for ViewModels, wrapping lifecycle handling functions.
- **`executeOperation`**: Asynchronous processor, automatically manages the Loading flag, catches Exceptions globally, and converts them into friendly error messages.
- **`ProviderStateListener` & `MultiProviderStateListener`**: Utility duo to listen to side-effects on the interface declaratively, completely eliminating boilerplate code (`StreamSubscription`, `initState`, `dispose`) and ensuring perfect type-safety.

#### 🎨 Sealed ViewState & Polymorphic ErrorState Architecture
To enhance flexibility and deep custom error control capability from the UI side, the state management system has been upgraded to a **Sealed ViewState** combined with **Polymorphic ErrorState** model:

##### 1. Sealed Class `ViewState`
`ViewState` is defined as a sealed class (Freezed Union) to ensure exhaustive matching when rendering UI:
* `ViewState.initial()`: Initialization state.
* `ViewState.loading()`: Executing task.
* `ViewState.success()`: Execution successful.
* `ViewState.error({ErrorState? error})`: Failed, attaching a customized `ErrorState` object.

##### 2. Unlimited Custom `ErrorState`
The utilizing side (Feature module) is free to extend `ErrorState` to define a separate error data structure for their business:
```dart
class MyCustomErrorState extends ErrorState {
  final String code;
  final String description;

  const MyCustomErrorState({required this.code, required this.description});

  @override
  Map<String, dynamic> toJson() => {
        'type': 'my_custom_error',
        'code': code,
        'description': description,
      };

  factory MyCustomErrorState.fromJson(Map<String, dynamic> json) =>
      MyCustomErrorState(
        code: json['code'] as String,
        description: json['description'] as String,
      );
}
```

##### 3. Polymorphic Serialization Mechanism & Fallback Registry
When the application state is stored or sent over a network environment (or offline cached like Hydrated Bloc/Hydrated Provider), `ViewStateModel` fully supports polymorphic serialization and deserialization via **`ErrorStateRegistry`**.

###### ❓ Why is `ErrorStateRegistry` needed?
Because `ErrorState` is an `abstract class`, code generation libraries like `json_serializable` when reading a JSON string **cannot know** which specific child entity (subclass) that JSON structure corresponds to for re-initialization. `ErrorStateRegistry` solves this problem by acting as a **Polymorphic Routing Map**:

1. Each `ErrorState` subclass needs to return a type identifier key (e.g., `'type': 'my_custom_error'`) in the `toJson()` method.
2. We register this identifier key along with its `fromJson` constructor into the registry.
3. During deserialization, the registry automatically extracts the `'type'` property from the JSON and calls the exactly corresponding constructor.

###### 📝 JSON Structure upon Serialization
When a `ViewStateModel` containing a custom `ErrorState` is serialized, the JSON structure is created as follows:
```json
{
  "state": {
    "state": "error",
    "error": {
      "type": "my_custom_error",
      "code": "ERR_AUTH_001",
      "description": "Login session has expired"
    }
  },
  "data": null,
  "message": "Login session has expired"
}
```

###### 🛠️ Registration Method & Registry Lifecycle
Registering Deserializers **MUST be done as early as possible in the application lifecycle** (before any restoration processes or offline state reading occur). The most ideal location is in the application's `main()` function at `app/lib/main.dart` or within the DI setup block:

```dart
// Register Deserializer in main() before running runApp()
void main() {
  WidgetsFlutterBinding.ensureInitialized();
  
  // Register all project-specific business error types
  ErrorStateRegistry.register('my_custom_error', MyCustomErrorState.fromJson);
  ErrorStateRegistry.register('validation_error', ValidationErrorState.fromJson);
  
  runApp(const MyApp());
}
```

###### 🛡️ Automatic Fallback Defense Mechanism (`RawErrorState`)
If the system deserializes an error JSON structure containing an `"type": "unknown_type"` that has never been registered in the system:
* The Registry will **automatically convert** that structure into a **`RawErrorState`** object.
* This `RawErrorState` class wraps the entire raw JSON Map of that error. This ensures **100% data is not lost**, the application **does not crash**, and developers can still access the raw data via the `.json` property if necessary:
  ```dart
  if (error is RawErrorState) {
    final rawJson = error.json; // Returns { "type": "unknown_type", "custom_field": "..." }
  }
  ```

##### 4. Flexible Error Task Configuration via `OperationConfig`
When configuring an asynchronous task, developers can optionally inject a conversion function from `AppFailure` to the desired `ErrorState` object by using the `errorStateBuilder` parameter:
```dart
await executeOperation(OperationConfig(
  operation: () => authRepository.login(username, password),
  errorStateBuilder: (failure) => MyCustomErrorState(
    code: 'LOGIN_FAILED',
    description: failure.message,
  ),
));
```

##### 5. Handling State Feedback On UI (Type-safe Exhaustive Matching)
Thanks to the Sealed nature of `ViewState`, the Presentation layer (like `BaseViewWidget`) can handle states extremely strictly via the auto-generated `.when()` or `.whenOrNull()` API:
```dart
return viewState.state.when(
  initial: () => const InitialWidget(),
  loading: () => const LoadingWidget(),
  success: () => const SuccessWidget(),
  error: (error) {
    if (error is MyCustomErrorState) {
      return SpecialErrorWidget(code: error.code);
    }
    return GeneralErrorWidget(message: viewState.message);
  },
);
```

##### 6. Declarative State Listening Mechanism
When an application needs to execute tasks that occur only once based on state changes (such as showing a Toast notification, popping up a Dialog, or navigating screens), listening manually with `StreamSubscription` in `initState` and `dispose` easily causes memory leaks and costs a lot of maintenance effort.

To thoroughly solve this problem, the `provider_state_management` package integrates two dedicated tools:
1. **`ProviderStateListener<P, T>`**: Listens to a single `BaseProvider`.
2. **`MultiProviderStateListener`**: Combines multiple input listeners without causing deep widget tree nesting (Deep Nesting).

###### Detailed Syntax of `ProviderStateListener`
```dart
ProviderStateListener<AuthProvider, UserEntity>(
  // Called when state switches to loading
  onLoading: (context) {
    // Example: show local loading HUD
  },
  // Called when state switches to success
  onSuccess: (context, user) {
    // Example: navigate to Dashboard
  },
  // Called when state switches to error, receives polymorphic ErrorState & message
  onError: (context, error, message) {
    if (error is AuthErrorState) {
      error.maybeWhen(
        invalidCredentials: () => AppOverlay.showToast(content: 'Invalid login credentials'),
        orElse: () => AppOverlay.showToast(content: message ?? 'An error occurred'),
      );
    }
  },
  // (Optional) Filter to control callback trigger condition
  listenWhen: (previous, current) => previous.state != current.state,
  child: Scaffold(...),
)
```

###### The "Blueprint Pattern" Design Of `MultiProviderStateListener`
To avoid nesting listener widgets causing unreadable source code, `MultiProviderStateListener` allows declaring a flat list of listeners by using lightweight `ProviderStateListenerEntry` configuration objects instead of manual widget nesting:

```dart
MultiProviderStateListener(
  listeners: [
    ProviderStateListenerEntry<AuthProvider, UserEntity>(
      onError: (context, error, message) => AppOverlay.showToast(content: message),
    ),
    ProviderStateListenerEntry<CartProvider, CartData>(
      onSuccess: (context, cart) => AppOverlay.showToast(content: 'Cart updated successfully'),
    ),
  ],
  child: MyScreenBody(),
)
```
* **Crucial Technical Note**: `ProviderStateListenerEntry` inherits from `ProviderStateListenerBase` and is NOT a widget. It acts as a "blueprint" defining listening behavior. When loaded into `MultiProviderStateListener`, the system automatically calls the `buildWithChild()` method to nest widgets in the most type-safe way possible, helping to keep intact the generic type arguments of each Provider to serve Flutter's dependency lookup.

### F. Core Bloc State Management (`packages/core/bloc_state_management`)
State management backbone for Features using BLoC architecture:
- **`BaseBloc` / `BaseCubit`**: Pure base classes, not constrained by complex logic, helping BLoC developers freely implement helpers, logging, or exception handling in BLoC's specific style.
- **`ViewState`**: Standardized state class (Freezed Union) (`initial`, `loading`, `success`, `error`) to use commonly for all screens, helping UI easily pattern-match without redefining states themselves.

## 🔌 3. DI Registration Mechanism and API Exposure (Micro-core Exposure)

Each Core module self-manages its dependency registration via `@InjectableInit.microPackage()` at its `lib/di/module.dart` file.

The main `app` package will load these modules as pre-dependencies at `injection.dart`.

**Ordering:** Keep infrastructure cores in `externalPackageModulesBefore`. Put `CoreBaseUiPackageModule` in `externalPackageModulesAfter` (via `_uiModules`) because it depends on app-local `ILanguageStorage` / `IThemeStorage`.

```dart
@InjectableInit(
  externalPackageModulesBefore: [
    ExternalModule(CoreCommonPackageModule),
    ExternalModule(CoreNetworkPackageModule),
    ExternalModule(CoreNotificationsPackageModule),
    ExternalModule(CoreStoragePackageModule),
    ExternalModule(CoreDiPackageModule),
  ],
  externalPackageModulesAfter: [
    ExternalModule(CoreBaseUiPackageModule),
    ExternalModule(ProviderStateManagementPackageModule),
    ExternalModule(BlocStateManagementPackageModule),
    // ... domain_*, data_*, feature_* micro-package modules
  ],
)
```
