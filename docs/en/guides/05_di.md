# Dependency Injection

**This guide answers:** which annotation do I use, where does my module get registered, and why does the app throw "not registered" at startup?

**After reading you can:** register any class with the right scope, understand module initialisation order, avoid the eager-singleton trap, and write lookups that survive a feature being removed.

---

## 1. The model: GetIt + Injectable, one module per package

Every package owns a DI module at `lib/di/module.dart`:

```dart
import 'package:injectable/injectable.dart';

@InjectableInit.microPackage()
void initMicroPackage() {}
```

`build_runner` turns that into `lib/di/module.module.dart`, exposing e.g. `CoreStoragePackageModule`. The app shell composes all of them in `apps/mobile/lib/di/injection.dart`.

Annotate a class and it lands in its own package's module automatically — you never edit generated files.

## 2. Choosing a scope

| Annotation | Lifetime | Use for | Real example |
|---|---|---|---|
| `@injectable` | New instance per resolve | Screen-scoped VMs / BLoCs | `HomeProfileBloc` |
| `@lazySingleton` | One instance, created on first resolve | App-wide controllers, storage owners | `AuthProvider`, `AuthLocalDataSource` |
| `@singleton` | One instance, created **during** DI init | Stateless app-wide services; navigators as `@Singleton(as: …)` | `AppRouter`, `AppBootStorage`, `AuthNavigatorImpl` |
| `@Injectable(as: I)` | Factory bound to an interface | Stateless contributions resolved on demand | `AuthActionHandlerImpl`, every `IFeatureLocalization` |
| `@LazySingleton(as: I)` | Singleton bound to an interface | Repositories, route modules | `AuthRepositoryImpl`, `NetworkConfigImpl`, `HomeNavDestination` |
| `@module` + `@preResolve` | Third-party / async construction | Types you don't own | `SharedPreferences`, a package's own Drift database |

> [!CAUTION]
> **Never register a screen-scoped controller as a singleton.** GetIt holds it forever, so the screen leaks and its state goes stale. See [`03_state_management.md`](03_state_management.md) §4.

### `@PostConstruct(preResolve: true)`

For a class needing async setup before anyone uses it:

```dart
@lazySingleton
class AuthLocalDataSource {
  AuthLocalDataSource(this._storageManager);

  final StorageManager _storageManager;

  late final _token = StorageValue<String>(
    _storageManager.getStorage(StorageType.secure),
    AuthStorageKeys.TOKEN,
  );

  late final _authUser = StorageValue<Map<String, dynamic>>(
    _storageManager.getStorage(StorageType.secure),
    AuthStorageKeys.AUTH_USER,
  );

  @PostConstruct(preResolve: true)
  Future<void> initialize() async {
    await Future.wait([_token.readFromStorage(), _authUser.readFromStorage()]);
  }

  // … getters and setters over _token / _authUser
}
```

`preResolve: true` makes DI `await` the setup during `configureDependencies()`, then register the *resolved* instance as a plain synchronous singleton — so later `getIt<AuthLocalDataSource>()` calls work synchronously.

> [!WARNING]
> **`@injectable` + `@PostConstruct` is wrong for a storage owner.** A factory hands out a brand-new instance per resolve, each with an **empty in-memory cache**, so synchronous getters return `null` even though the value is on disk. Storage owners must be `@lazySingleton` or `@singleton`.

## 3. Module initialisation order

This is the part that bites people. The order is declared once, in each app's `app_manifest.yaml` under `di_groups`, and `composer sync` generates it into `apps/<id>/lib/di/injection.dart`:

```dart
const _externalModulesBefore = [..._coreModules];
const _externalModulesAfter = [
    ..._notificationsModules,
    ..._shellModules,
    ..._uiModules,
    ..._domainModules,
    ..._dataModules,
    ..._featureModules,
    ..._otherModules,
];
```

Resulting sequence:

| # | Group | Contents |
|---|---|---|
| 1 | `_coreModules` (**before**) | common, network, storage, database, di |
| – | *the app's own registrations* | the app's `lib/` — in the sample only `FirebaseModule` (`apps/mobile/lib/firebase/firebase_module.dart`) |
| 2 | `_notificationsModules` | `core_notifications` — `PushNotificationService` |
| 3 | `_shellModules` | `platform_app_shell` — `AppRouter`, `AppProvider`, `DeeplinkProvider`, `AppBootStorage`, `ILanguageStorage`, `IThemeStorage`, `NetworkConfig`, `SslPinningConfig` |
| 4 | `_uiModules` | `CoreBaseUiPackageModule` |
| 5 | `_domainModules` | domain_core, then each module's domain package |
| 6 | `_dataModules` | data_core, then each module's data package |
| 7 | `_featureModules` | each module's feature package |
| 8 | `_otherModules` | provider / bloc state management |

Injectable runs a package's *own* registrations between the two phases. The app keeps that slot for what identifies it and nothing else — its per-flavour `FirebaseOptions`; everything else arrives through a group. Three placements are deliberate and must not be "tidied up":

**(a) `shell` comes before `ui`.**
`ThemeProvider` and `LanguageProvider` in `core_base_ui` inject `IThemeStorage` / `ILanguageStorage`, whose implementations live in `platform_app_shell` (`platform/app_shell/lib/di/theme_storage_impl.dart`, `language_storage_impl.dart`). Reverse the two groups and the providers resolve their storage before it exists.

**(b) A package that opens a database runs after everything that contributes a migration to it.**
Opening a database is `@preResolve`, and opening it is what runs the collected `IDatabaseMigration` steps — so every step must be registered before the open. Inside the owning package, `@Order(1)` on the open settles that (`modules/cache/data/lib/di/module.dart`): injectable registers a package's entries in ascending `@Order`, so the package's own steps (default order 0) come first. `@Order` does not reach across modules, though. `data_cache` (the `cache` sample module) opens its `CacheDatabase` while the `data` group initialises, so a migration contributed by a package in a *later* group — a feature, say — would simply not be there yet, and would be skipped without an error. A database of your own needs the same `@Order(1)` on its open. `core_database` itself registers nothing (it is mechanism only), which is why it can sit in `core`.

**(c) `notifications` is not in `core`.**
`PushNotificationService` is an eager `@singleton` that injects `FirebaseOptions`, and those are registered by the app itself, between the phases — they identify one bundle ID, so no platform package may own them. From `before` the service would resolve them before they exist and throw at boot. An app that sends no push notifications drops the group, and needs no `lib/firebase/` either.

## 4. The eager-singleton trap

> [!CAUTION]
> **An eager `@Singleton` must not depend on a type registered by a later module.** The instance is constructed *during* registration, so a dependency that has not been registered yet throws
> `Object/factory with type X is not registered inside GetIt` — at app startup, on every launch.
>
> **`flutter analyze` cannot catch this.** It is a runtime ordering fault, not a type error.

Worked example: `ThemeStorageImpl` is an eager `@Singleton(as: IThemeStorage)` in the `shell` group. Its only constructor dependency is `StorageManager`, which `core_storage` registered in group 1 — the correct direction. If it also injected, say, `AuthLocalDataSource` from `data_auth` (group 6), boot would throw on every launch. The fix is one word — make it `@LazySingleton` — or, better, not to depend on a module at all.

That is what `NetworkConfigImpl` does. It used to inject `AuthLocalDataSource` and `RefreshTokenUseCase` and had to be lazy for exactly this reason. It now takes only `ILanguageStorage` from its own group and reads the session through `IAuthSessionGateway` at call time:

```dart
@LazySingleton(as: NetworkConfig)
class NetworkConfigImpl implements NetworkConfig {
  NetworkConfigImpl(this._languageStorage);

  /// Null in a build that composes no auth module.
  IAuthSessionGateway? get _session => getItOrNull<IAuthSessionGateway>();
  // ...
}
```

**How to verify.** The generated `apps/mobile/lib/di/injection.config.dart` holds only the module order (one `…PackageModule().init(gh)` per package). The per-type registrations are in each package's generated `lib/di/module.module.dart`: check that every `gh.singleton<...>(...)` there (no `lazy`) only calls `gh<Dep>()` for types registered above it in that file or by a module whose `init` runs earlier in `injection.config.dart`.

Rule of thumb: if a class depends on anything from `domain_*`, `data_*` or `feature_*`, make it **lazy**.

## 5. Dual registration — binding one instance to two interfaces

> [!WARNING]
> **GetIt resolves by the exact registered type. It does not walk the supertype chain.**

`NetworkConfig implements SslPinningConfig`, but registering `NetworkConfigImpl` `as: NetworkConfig` leaves `getItOrNull<SslPinningConfig>()` returning `null` — and `AppInitializer` then silently skips certificate pinning on staging and production. The explicit binding in `platform/app_shell/lib/di/network_binding_module.dart` is what makes both types resolve:

```dart
@module
abstract class NetworkBindingModule {
  @lazySingleton
  SslPinningConfig bindSslPinningConfig(NetworkConfig config) => config;
}
```

The parameter is typed `NetworkConfig`, so the upcast is compiler-checked — no `as` cast. The same pattern registers an agnostic stream twice (concrete `@singleton` for the owner, interface binding for consumers) — see [`10_cross_feature.md`](10_cross_feature.md).

### Binding third-party libraries

The same `@module` mechanism is how a type you do not own enters the container. `platform/storage/lib/di/module.dart`:

```dart
@module
abstract class CoreStorageDiModule {
  @preResolve
  Future<SharedPreferences> getSharedPreferences() async {
    return SharedPreferences.getInstance();
  }
}
```

`@preResolve` is what makes `configureDependencies()` **await** this before returning, so everything downstream can take `SharedPreferences` as a plain constructor parameter instead of a `Future`. Use it only where construction is genuinely async; a `@lazySingleton` getter is enough for anything that is not.

A module is also where you build a client from another package's object. `modules/auth/data/lib/di/register_module.dart` turns the shared `Dio` into this module's Retrofit data source:

```dart
@module
abstract class RegisterModule {
  @lazySingleton
  AuthRemoteDataSource authRemoteDataSource(Dio dio) =>
      AuthRemoteDataSource(dio);
}
```

Calling `SharedPreferences.getInstance()` or constructing `Dio` inside a repository instead would hide the dependency from the container and leave no seam for a fake in tests. That is the whole reason these live in a `@module`.

## 6. Resolution helpers

Defined in `platform/kernel/lib/src/di/service_locator.dart`, re-exported by `platform/common/lib/di/module.dart`:

| Helper | Missing registration | Use when |
|---|---|---|
| `getIt<T>()` | **Throws** | T is guaranteed — core infra you always ship |
| `getItOrNull<T>()` | Returns `null` | T belongs to a feature that may be removed |
| `getAll<T>()` | **Throws** | Never, for optional contributions |
| `getAllOrEmpty<T>()` | Returns `const []` | Collecting multi-instance contributions |

```dart
Iterable<T> getAllOrEmpty<T extends Object>({...}) {
  if (!getIt.isRegistered<T>()) {
    return const [];
  }
  return getIt.getAll<T>(...);
}
```

This is what makes a feature removable. The shell collects routes, tabs and localisation delegates with `getAllOrEmpty`, and optional singletons with `getItOrNull` + a fallback:

```dart
final tabs = getAllOrEmpty<INavDestinationModule>();          // none composed → []
final entry = getItOrNull<IAppEntryLocation>()?.path;         // none composed → null
final boot = getItOrNull<AppBootStorage>();                   // shell-owned first-launch flag
// Resolved in AppRouter.entryLocation — see 04_routing.md for the full shape.
```

> [!NOTE]
> `getIt.enableRegisteringMultipleInstancesOfOneType()` is called in `configureDependencies()`, before `getIt.init` — that is what allows several packages to each register their own `IFeatureRouteModule`. Without it the second registration throws at boot (§9).

## 7. Constructor injection only

> [!CAUTION]
> **Never call `getIt<T>()` inside business logic** — ViewModels, Repositories, UseCases. Hidden lookups make a class untestable (you cannot pass a fake) and hide its real dependencies.

```dart
// Correct — dependencies are visible and mockable
@injectable
class LoginUseCase extends BaseUseCase<UserEntity, LoginParams> {
  LoginUseCase(this._authRepository);
  final IAuthRepository _authRepository;
}
```

Service-locator calls are acceptable only at composition seams: route `build()` methods, widget-tree wiring, and the app shell's assembly code.

## 8. Adding a new package to DI

1. Create `lib/di/module.dart` with `@InjectableInit.microPackage()` (the module generator does this).
2. Annotate your classes.
3. Run `dart run build_runner build --workspace`.
4. Add it to the app's `app_manifest.yaml` — a module under `modules:`, or a platform package under the right `di_groups` entry — then run `dart tools/composer/composer.dart sync`. **Never edit `injection.dart` by hand**: its module lists sit between `composer:managed` markers and CI Gate 0 fails on drift.
5. Verify the order: module order in `injection.config.dart`, your type's registration and its `gh<Dep>()` calls in the package's `lib/di/module.module.dart`.

### `ignoreUnregisteredTypesInPackages`

No module needs arguments on `@InjectableInit.microPackage()` except `core_notifications`, which passes `ignoreUnregisteredTypesInPackages: ['firebase_core']`: the `FirebaseOptions` it injects is registered by each app's `lib/firebase/firebase_module.dart`, never by a package module. Do not add the argument to silence a registration that is genuinely missing.

## 9. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `type X is not registered` at startup | Eager singleton depends on a later module | Switch to `@LazySingleton` (§4) |
| `getItOrNull<Supertype>()` returns null | GetIt does not resolve supertypes | Add a `@module` binding (§5) |
| Storage getter returns `null` despite data on disk | Owner is `@injectable`; cache empty | Use `@lazySingleton` + `@PostConstruct(preResolve: true)` (§2) |
| Boot throws `ArgumentError: Type IFeatureRouteModule is already registered inside GetIt.` (or `INavDestinationModule`, `IFeatureLocalization`, `IAppTreeWrapper` — any type several packages contribute) | Multi-registration is off. GetIt 9 never silently keeps one: a second **unnamed** registration of a type throws unless `allowRegisterMultipleImplementationsOfoneType` is set | `getIt.enableRegisteringMultipleInstancesOfOneType()` must run in the app's `configureDependencies()` (`apps/<id>/lib/di/injection.dart`, hand-written, outside the `composer:managed` markers) **before** `getIt.init`. A test registering two of one type calls it too (`modules/dashboard/feature/test/dashboard_page_test.dart`) |
| Stale screen state after re-entry | Screen controller is a singleton | Switch to `@injectable` |
| `getAll<T>()` throws | No implementation registered | Use `getAllOrEmpty<T>()` |

## Checklist

- [ ] Screen controllers `@injectable`; global ones `@lazySingleton`
- [ ] Anything depending on domain/data/feature types is **lazy**
- [ ] Storage owners are singletons with `@PostConstruct(preResolve: true)`
- [ ] New package composed in each `app_manifest.yaml` — a module under `modules:`, a platform package in the correct `di_groups` entry — then `composer sync`
- [ ] Order verified: module order in generated `injection.config.dart`, per-type registrations in the package's `lib/di/module.module.dart`
- [ ] Optional cross-feature lookups use `getItOrNull` / `getAllOrEmpty`
- [ ] No `getIt<T>()` inside VMs, repositories or use cases
