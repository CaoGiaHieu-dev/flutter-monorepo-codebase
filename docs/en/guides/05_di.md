# Dependency Injection

## Goal

You register any class with the right scope, compose a new package into an app, and write lookups that survive a feature being removed. When the app throws "not registered" at startup, you know how to find the cause.

## Prerequisites

- **How DI is assembled**: one module per package, the module order each app declares, and why three placements must not move — [`../architecture/06_app_shell.md` § 3](../architecture/06_app_shell.md#3-di-assembly--and-why-the-order-matters). Read it before you change a manifest's `di_groups`.
- A package with `lib/di/module.dart` — the module generator writes it ([`01_new_feature.md`](01_new_feature.md), [`02_new_domain_data.md`](02_new_domain_data.md)).

## 1. Choose a scope

| Annotation | Lifetime | Use for | Real example |
|---|---|---|---|
| `@injectable` | New instance per resolve | Screen-scoped VMs / BLoCs | `HomeProfileBloc` |
| `@lazySingleton` | One instance, created on first resolve | App-wide controllers, storage owners | `AuthProvider`, `AuthLocalDataSource` |
| `@singleton` | One instance, created **during** DI init | Stateless app-wide services; navigators as `@Singleton(as: …)` | `AppRouter`, `AppBootStorage`, `AuthNavigatorImpl` |
| `@Injectable(as: I)` | Factory bound to an interface | Stateless contributions resolved on demand | `AuthActionHandlerImpl`, every `IFeatureLocalization` |
| `@LazySingleton(as: I)` | Singleton bound to an interface | Repositories, route modules | `AuthRepositoryImpl`, `NetworkConfigImpl`, `HomeNavDestination` |
| `@module` + `@preResolve` | Third-party / async construction | Types you don't own | `SharedPreferences`, a package's own Drift database |

A screen-scoped controller is never a singleton (RULE-10): GetIt would hold it forever, so the screen leaks and its state goes stale. See [`03_state_management.md`](03_state_management.md) § 9.

Rule of thumb: if a class depends on anything from `domain_*`, `data_*` or `feature_*`, make it **lazy** (RULE-13, step 8).

## 2. Hydrate async state before first use

For a class that needs async setup before anyone uses it, add `@PostConstruct(preResolve: true)`:

```dart
@lazySingleton
class AuthLocalDataSource {
  AuthLocalDataSource(this._storageManager);

  final StorageManager _storageManager;

  late final _token = StorageValue<String>(
    _storageManager.getStorage(StorageType.secure),
    AuthStorageKeys.TOKEN,
  );

  /// Hydrates the cache from disk at startup, so [getUserToken] is correct from
  /// the first read.
  @PostConstruct(preResolve: true)
  Future<void> initialize() => _token.readFromStorage();

  Future<void> saveUserToken(String token) => _token.save(token);

  String? getUserToken() => _token.value;

  Future<void> clearUserToken() => _token.remove();
}
```

`preResolve: true` makes DI `await` the setup during `configureDependencies()`. It then registers the *resolved* instance as a plain synchronous singleton, so later `getIt<AuthLocalDataSource>()` calls work synchronously.

> [!WARNING]
> **`@injectable` + `@PostConstruct` is wrong for a storage owner.** A factory hands out a brand-new instance per resolve, each with an **empty in-memory cache**. Synchronous getters then return `null` even though the value is on disk. Storage owners must be `@lazySingleton` or `@singleton` (RULE-45).

## 3. Register a type you do not own

A type you do not own enters the container through a `@module`. `platform/infra/storage/lib/di/module.dart`:

```dart
@module
abstract class CoreStorageDiModule {
  @preResolve
  Future<SharedPreferences> getSharedPreferences() async {
    return SharedPreferences.getInstance();
  }
}
```

`@preResolve` makes `configureDependencies()` **await** this before returning. Everything downstream can then take `SharedPreferences` as a plain constructor parameter instead of a `Future`. Use it only where construction is genuinely async; a `@lazySingleton` getter is enough for anything that is not.

A module is also where you build a client from another package's object. `modules/auth/data/lib/di/module.dart` turns the shared `Dio` into this module's Retrofit data source:

```dart
@module
abstract class AuthDataDiModule {
  /// Builds the Retrofit client from the shared [Dio] that `core_network`
  /// registers, so the data source inherits its interceptor chain. Built here,
  /// not inside the repository, so a test can pass a fake in.
  @lazySingleton
  AuthRemoteDataSource authRemoteDataSource(Dio dio) =>
      AuthRemoteDataSource(dio);
}
```

That `Dio` is the one `core_network` registers (`NetworkModule` in `platform/infra/network/lib/di/network_module.dart`), already carrying the interceptor chain ([`08_networking.md`](08_networking.md)). The `@module` classes in this repo are named after their package and layer (`CoreStorageDiModule`, `AuthDataDiModule`, `AuthDiModule`, `DataCacheDiModule`).

Calling `SharedPreferences.getInstance()` or constructing `Dio` inside a repository instead would hide the dependency from the container. It would also leave no seam for a fake in tests. That is the whole reason these live in a `@module`.

## 4. Bind a second interface to one instance

> [!WARNING]
> **GetIt resolves by the exact registered type. It does not walk the supertype chain** (RULE-14).

Registering `AuthProvider` as a `@lazySingleton` does not make it resolvable as `ISessionState`, although `AuthProvider implements ISessionState`; and `@LazySingleton(as: I)` binds exactly one interface. Bind each further interface through a `@module` — `modules/auth/feature/lib/di/module.dart`, which binds three:

```dart
@module
abstract class AuthDiModule {
  /// The neutral session stream other features listen to.
  @singleton
  ISessionStatusStream bindISessionStatusStream(AuthStatusStreamImpl impl) =>
      impl;

  /// The shell-facing session view: boot sequencing and the failure channel.
  @lazySingleton
  ISessionState bindISessionState(AuthProvider provider) => provider;

  /// `GoRouter.refreshListenable`: routing reacts to sign-in and sign-out.
  @lazySingleton
  ISessionRefreshListenable bindISessionRefreshListenable(
    AuthProvider provider,
  ) => provider;
}
```

The parameter is typed with the concrete class, so the upcast is compiler-checked — no `as` cast. Match the scope of what you bind: `AuthProvider` is lazy, so its two bindings are lazy too (an eager binding would construct the provider while the module registers); `AuthStatusStreamImpl` is an eager `@singleton`, and so is its interface binding. Without the bindings the shell's `getItOrNull<ISessionState>()` returns `null` and the app treats every user as signed out; an app that declares `session: provided` fails `checkAppContract` (`C02`) in its smoke test. The stream is the cross-feature pattern: a concrete `@singleton` for the owner, an interface binding for consumers ([`10_cross_feature.md`](10_cross_feature.md)).

## 5. Resolve optional contributions safely

The helpers are defined in `platform/foundation/kernel/lib/src/service_locator.dart` (`platform_kernel`), which `core_common` re-exports, so `package:core_common/core_common.dart` gives you them too:

| Helper | Missing registration | Use when |
|---|---|---|
| `getIt<T>()` | **Throws** | T is guaranteed — core infra you always ship |
| `getItOrNull<T>()` | Returns `null` | T belongs to a feature that may be removed |
| `getAll<T>()` | **Throws** | Never, for optional contributions |
| `getAllOrEmpty<T>()` | Returns `const []` | Collecting multi-instance contributions |

```dart
Iterable<T> getAllOrEmpty<T extends Object>({
  dynamic param1,
  dynamic param2,
  bool fromAllScopes = false,
  String? onlyInScope,
}) {
  if (!getIt.isRegistered<T>()) return const [];
  return getIt.getAll<T>(
    param1: param1,
    param2: param2,
    fromAllScopes: fromAllScopes,
    onlyInScope: onlyInScope,
  );
}
```

This is what makes a feature removable (RULE-12, enforced by `arch_check` R8). The shell collects routes, tabs and localisation delegates with `getAllOrEmpty`, and optional singletons with `getItOrNull` + a fallback:

```dart
final tabs = getAllOrEmpty<INavDestinationModule>();                          // none composed → []
final entry = getItOrNull<IAppEntryLocation>();                               // none composed → null
final viewed = getItOrNull<AppBootStorage>()?.viewedOnboard ?? false;         // shell-owned first-launch flag
// Resolved in AppRouter.entryLocation — see 04_routing.md for the full shape.
```

A class that needs an optional contract does not take it as a constructor parameter: it resolves it at call time. `NetworkConfigImpl` (`platform/shell/adapters/lib/src/network_config_impl.dart`) reads `ISessionGateway? get _session => getItOrNull<ISessionGateway>();` inside its callbacks, so it constructs whether or not an auth module is composed.

> [!NOTE]
> Each app's generated `configureDependencies({String? environment, ServiceLocator? locator})` (`apps/<id>/lib/di/injection.dart`; no app writes it) calls `enableRegisteringMultipleInstancesOfOneType()`, then `registerProfileDefaults`, then `init` — all on the `locator` it is given, which is `getIt` in a real boot. Multi-registration is what allows several packages to each register their own `IFeatureRouteModule`; without it the second registration throws at boot (see *Troubleshooting*). It has one more effect: GetIt then keeps the **first** registration of a type, so replacing a shell-owned type by registering your own is unsupported — an app registration beats a type from an `after` group and loses to one from `before`. The seams for what apps used to override this way are the profile and the hooks ([`13_app_composition.md`](13_app_composition.md) § 10).

## 6. Inject through the constructor

Never call `getIt<T>()` inside business logic — ViewModels, Repositories, UseCases (RULE-11). A hidden lookup makes a class untestable, because you cannot pass a fake, and it hides the class's real dependencies.

```dart
// Correct — dependencies are visible and mockable
@injectable
class LoginUseCase extends BaseUseCase<UserEntity, LoginParams> {
  LoginUseCase(this._repository);
  final IAuthRepository _repository;
}
```

Service-locator calls are acceptable only at composition seams: route `build()` methods, widget-tree wiring, and the app shell's assembly code.

The app's profile sections are constructor parameters like any other. `runShellApp` registers `NetworkProfile`, `LocaleProfile`, `ThemeProfile`, `RouterProfile` and `PlatformFacts` before the graph is built (and `registerProfileDefaults` adds the template's default for any section still missing), so a class takes the section it reads — optional, with a `const` default for a hand-built object, as `ThemeStorageImpl(this._storageManager, [ThemeProfile profile = const ThemeProfile()])` does in `platform/shell/adapters/lib/src/theme_storage_impl.dart`. What a section holds, and how an app sets it: [`13_app_composition.md`](13_app_composition.md) § 4.

## 7. Add a new package to DI

1. Create `lib/di/module.dart` with `@InjectableInit.microPackage()` (the module generator does this). Every package an app composes needs it, even one that registers nothing (`core_database`, the state-management bases); a package no `di_groups` entry lists — `platform_kernel`, `core_responsive`, an `<id>_api` — has none, and `composer sync` leaves a package without the marker out of `injection.dart` (RULE-15). `lib/di/` holds DI only — the `microPackage()` marker, the generated `module.module.dart` and the package's `@module` classes (in `module.dart`, or a file beside it such as `core_network`'s `network_module.dart`); the classes you annotate live under `lib/src/`.
2. Annotate your classes.
3. Run `dart run build_runner build --workspace`, then `dart tools/barrel_generator/generate.dart <package>/lib` if you added a file under `lib/` (RULE-75).
4. Add it to the app's `app_manifest.yaml` — a module under `modules:`, or a platform package under the right `di_groups` entry — then run `dart tools/composer/composer.dart sync`. Never edit `injection.dart` by hand: the imports and the module lists with the `configureDependencies()` entry point sit between `composer:managed` markers, outside them the file holds only comments, and CI Gate 0 fails on drift or on code outside the regions (RULE-16). If the package registers a contract the shell catalogues (a splash, a reporter, tabs), the app's `capabilities:` must say so, and `composer verify` tells you when it does not ([`13_app_composition.md`](13_app_composition.md) § 6).
5. Verify with the DI smoke test (*Verify* below). A plugin your registration touches during DI needs its test double there (RULE-63).

### Pass no arguments to `microPackage()`

No module needs arguments on `@InjectableInit.microPackage()` (RULE-15), except `core_notifications`. It passes `ignoreUnregisteredTypesInPackages: ['firebase_core']`, because the `FirebaseOptions` it injects is registered by each app's `lib/firebase/firebase_module.dart`, never by a package module. Do not add the argument to silence a registration that is genuinely missing.

## 8. Diagnose "not registered" at startup

> [!CAUTION]
> **An eager `@Singleton` must not depend on a type registered by a later module** (RULE-13). The instance is constructed *during* registration, so a dependency that has not been registered yet throws
> `Object/factory with type X is not registered inside GetIt` — at app startup, on every launch.
>
> **`flutter analyze` cannot catch this**: it is a runtime ordering fault. Each app's `test/di_smoke_test.dart` boots the real graph for every flavor and catches it in CI Gate 3 (RULE-63).

To find the cause:

1. Run the smoke test (*Verify*). It fails with the type that is missing.
2. Open the generated `apps/mobile/lib/di/injection.config.dart`. It holds the module order — one `…PackageModule().init(gh)` per package — and the app's own registrations (`FirebaseModule`'s per-flavor `FirebaseOptions` in mobile) between the `core` group and the rest.
3. Open the generated `lib/di/module.module.dart` of the package that registers the failing class. Every `gh.singleton<...>(...)` there (no `lazy`) may only call `gh<Dep>()` for types registered above it in that file, or by a module whose `init` runs earlier in `injection.config.dart`.
4. Fix it with one word — `@LazySingleton` — or, better, remove the cross-module constructor dependency. The worked example is in [`../architecture/06_app_shell.md` § 3](../architecture/06_app_shell.md#the-eager-singleton-ordering-trap).

## Verify

```bash
dart run build_runner build --workspace                  # regenerates every module.module.dart
dart tools/composer/composer.dart verify                 # ✅ Generated artifacts are up to date.
cd apps/mobile && flutter test test/di_smoke_test.dart   # All tests passed!
cd apps/admin && flutter test test/di_smoke_test.dart    # All tests passed!
```

The smoke test registers the app's profile, then runs `configureDependencies()` for every flavor the manifest declares, through a `FactoryRecorder` (`platform_app_shell`) standing in for the locator — GetIt's own `findAll(callFactories: true)` calls only the synchronous factories with `null` arguments and names nothing when one throws. It then builds every lazy singleton, builds every `@injectable` factory one by one, and holds the graph to the manifest's `capabilities:` with `checkAppContract`. A factory that cannot be built fails the test naming its type (`F02`). A factory is built with `null` for each nullable `@factoryParam`, and an async factory is awaited. One with a **non-nullable** `@factoryParam` — a detail screen's controller that needs the id its route passes — is correct code that this test cannot build; list its type name and the reason in the test's `_factoriesNeedingArguments` map, or the test fails with `F01` (a stale or reason-less entry fails too: `F03`, `F04`). A passing run is the proof that your registration and its order are right; reading generated files is not.

Review checklist:

- [ ] Screen controllers `@injectable`; global ones `@lazySingleton`
- [ ] Anything depending on domain/data/feature types is **lazy**
- [ ] Storage owners are singletons with `@PostConstruct(preResolve: true)`
- [ ] New package composed in each `app_manifest.yaml` — a module under `modules:`, a platform package in the correct `di_groups` entry — then `composer sync`
- [ ] Order verified by each app's `test/di_smoke_test.dart` (RULE-13, RULE-63)
- [ ] Optional cross-feature lookups use `getItOrNull` / `getAllOrEmpty`
- [ ] No `getIt<T>()` inside VMs, repositories or use cases

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `type X is not registered` at startup | Eager singleton depends on a later module | Switch to `@LazySingleton` (step 8) |
| `getItOrNull<Supertype>()` returns null | GetIt does not resolve supertypes | Add a `@module` binding (step 4) |
| Storage getter returns `null` despite data on disk | Owner is `@injectable`; cache empty | Use `@lazySingleton` + `@PostConstruct(preResolve: true)` (step 2) |
| Boot throws `ArgumentError: Type IFeatureRouteModule is already registered inside GetIt.` (or `INavDestinationModule`, `IFeatureLocalization`, `IAppTreeWrapper` — any type several packages contribute) | Multi-registration is off. GetIt 9 never silently keeps one: a second **unnamed** registration of a type throws unless `allowRegisterMultipleImplementationsOfoneType` is set | `getIt.enableRegisteringMultipleInstancesOfOneType()` must run in the app's `configureDependencies()` (`apps/<id>/lib/di/injection.dart`, generated by `composer sync` — if it is missing, run `sync`) **before** `getIt.init`. A test registering two of one type calls it too (`platform/shell/app_shell/test/app_router_test.dart`) |
| Smoke test fails with `F01` `<Type>` (a non-nullable `@factoryParam`) or `F02` `<Type>` (the factory threw) | `F01`: the test calls every factory without an argument. `F02`: the factory's own dependency is missing or its body throws | `F01`: make the parameter nullable, or list the type with a reason in `_factoriesNeedingArguments` (*Verify*). `F02`: fix the registration the message names |
| Stale screen state after re-entry | Screen controller is a singleton | Switch to `@injectable` |
| `getAll<T>()` throws | No implementation registered | Use `getAllOrEmpty<T>()` |
| A new registration is not picked up | Hot reload does not rebuild the DI graph | Re-run `build_runner`, then **full restart** |
