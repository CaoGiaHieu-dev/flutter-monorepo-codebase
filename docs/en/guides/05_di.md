# Dependency Injection

**This guide answers:** which annotation do I use, where does my module get registered, and why does the app throw "not registered" at startup?

**After reading you can:** register any class with the right scope, understand module initialisation order, avoid the eager-singleton trap, and write lookups that survive a feature being removed.

---

## 1. The model: GetIt + Injectable, one module per package

Every package owns a DI module at `lib/di/module.dart`:

```dart
import 'package:injectable/injectable.dart';

@InjectableInit.microPackage()
void initMicroPackage() {}
```

`build_runner` turns that into `lib/di/module.module.dart`, exposing e.g. `CoreStoragePackageModule`. The app shell composes all of them in `app/lib/di/injection.dart`.

Annotate a class and it lands in its own package's module automatically — you never edit generated files.

## 2. Choosing a scope

| Annotation | Lifetime | Use for | Real example |
|---|---|---|---|
| `@injectable` | New instance per resolve | Screen-scoped VMs / BLoCs | `HomeProfileBloc` |
| `@lazySingleton` | One instance, created on first resolve | App-wide controllers, storage owners | `AuthProvider`, `AuthLocalDataSource` |
| `@singleton` | One instance, created **during** DI init | Stateless app-wide services | `AppRouter`, `AppBootStorage` |
| `@Injectable(as: I)` | Factory bound to an interface | Repositories with per-use state | `AuthRepositoryImpl` |
| `@LazySingleton(as: I)` | Singleton bound to an interface | Repositories, navigators, route modules | `NetworkConfigImpl`, `HomeDashboardTabModule` |
| `@module` + `@preResolve` | Third-party / async construction | SDKs you don't own | `SharedPreferences`, `GoogleSignIn` |

> [!CAUTION]
> **Never register a screen-scoped controller as a singleton.** GetIt holds it forever, so the screen leaks and its state goes stale. See [`03_state_management.md`](03_state_management.md) §4.

### `@PostConstruct(preResolve: true)`

For a class needing async setup before anyone uses it:

```dart
@lazySingleton
class AuthLocalDataSource {
  AuthLocalDataSource(this._storageManager);

  final StorageManager _storageManager;

  late final _token = StorageValue<String>(
    _storageManager.getStorage(StorageType.secure),
    AuthStorageKeys.TOKEN,
  );

  @PostConstruct(preResolve: true)
  Future<void> initialize() async {
    await Future.wait([_token.readFromStorage(), _authUser.readFromStorage()]);
  }
}
```

`preResolve: true` makes DI `await` the setup during `configureDependencies()`, then register the *resolved* instance as a plain synchronous singleton — so later `getIt<AuthLocalDataSource>()` calls work synchronously.

> [!WARNING]
> **`@injectable` + `@PostConstruct` is wrong for a storage owner.** A factory hands out a brand-new instance per resolve, each with an **empty in-memory cache**, so synchronous getters return `null` even though the value is on disk. Storage owners must be `@lazySingleton` or `@singleton`.

## 3. Module initialisation order

This is the part that bites people. `app/lib/di/injection.dart`:

```dart
@InjectableInit(
  externalPackageModulesBefore: [..._coreModules],
  externalPackageModulesAfter: [
    ..._uiModules,
    ..._domainModules,
    ..._dataModules,
    ..._featureModules,
    ..._otherModules,
    ..._databaseModules,
  ],
)
```

Resulting sequence:

| # | Group | Contents |
|---|---|---|
| 1 | `_coreModules` (**Before**) | common, network, notifications, storage, di |
| 2 | *app-local* | `AppRouter`, `AppProvider`, `DeeplinkProvider`, `AppBootStorage`, `ILanguageStorage`, `IThemeStorage`, `NetworkConfig`, `SslPinningConfig` |
| 3 | `_uiModules` | `CoreBaseUiPackageModule` |
| 4 | `_domainModules` | domain_core, domain_auth, domain_language |
| 5 | `_dataModules` | data_core, data_auth, data_language |
| 6 | `_featureModules` | auth, dashboard, home, onboarding, settings, splash |
| 7 | `_otherModules` | provider / bloc state management |
| 8 | `_databaseModules` | `CoreDatabasePackageModule` |

Two placements are deliberate and must not be "tidied up":

**(a) `CoreBaseUiPackageModule` sits in `_uiModules`, not `_coreModules`.**
`ThemeProvider` and `LanguageProvider` inject `IThemeStorage` / `ILanguageStorage`, whose implementations are **app-local** (`app/lib/di/theme_storage_impl.dart`, `language_storage_impl.dart`) and therefore registered in step 2. Running core_base_ui in step 1 would resolve them before they exist.

**(b) `CoreDatabasePackageModule` runs LAST.**
Opening the database is `@preResolve`, and opening it is what runs the collected `IDatabaseMigration` steps. Any package contributing a migration must have registered it *first*, so the database module deliberately trails every domain, data and feature module. This is safe because every database consumer is a lazy singleton — nothing resolves it during startup.

## 4. The eager-singleton trap

> [!CAUTION]
> **An eager `@Singleton` must not depend on a type registered by a later module.** The instance is constructed *during* registration, so a dependency that has not been registered yet throws
> `Object/factory with type X is not registered inside GetIt` — at app startup, on every launch.
>
> **`flutter analyze` cannot catch this.** It is a runtime ordering fault, not a type error.

Real case: `NetworkConfigImpl` (app-local, step 2) depends on `AuthLocalDataSource`, which lives in `data_auth` (step 5). Registering it eagerly crashed the boot. The fix is one word:

```dart
/// Registered lazily (not eager `@Singleton`) because [AuthLocalDataSource]
/// lives in `data_auth`, whose module is initialized after this app-local DI
/// block runs. Its only consumer, `ApiClient`, is itself `@lazySingleton`,
/// so deferring construction here is safe.
@LazySingleton(as: NetworkConfig)
class NetworkConfigImpl implements NetworkConfig { ... }
```

**How to verify.** Read the generated `app/lib/di/injection.config.dart` and check that every `gh.singleton<...>(...)` (no `lazy`) only references types registered above it:

```dart
gh.lazySingleton<_i309.NetworkConfig>(
  () => _i52.NetworkConfigImpl(
    gh<_i700.AuthLocalDataSource>(),
    gh<_i472.ILanguageStorage>(),
    gh<_i693.RefreshTokenUseCase>(),
  ),
);
```

Rule of thumb: if a class depends on anything from `domain_*`, `data_*` or `feature_*`, make it **lazy**.

## 5. Dual registration — binding one instance to two interfaces

> [!WARNING]
> **GetIt resolves by the exact registered type. It does not walk the supertype chain.**

`NetworkConfig implements SslPinningConfig`, but registering `NetworkConfigImpl` `as: NetworkConfig` left `getItOrNull<SslPinningConfig>()` returning `null` — so `AppInitializer` silently skipped certificate pinning on staging and production. The fix, `app/lib/di/network_binding_module.dart`:

```dart
@module
abstract class NetworkBindingModule {
  @lazySingleton
  SslPinningConfig bindSslPinningConfig(NetworkConfig config) => config;
}
```

The parameter is typed `NetworkConfig`, so the upcast is compiler-checked — no `as` cast. The same pattern registers an agnostic stream twice (concrete `@singleton` for the owner, interface binding for consumers) — see [`10_cross_feature.md`](10_cross_feature.md).

### Binding third-party SDKs

The same `@module` mechanism is how SDK singletons enter the container. `packages/data/auth/lib/di/register_module.dart`:

```dart
@module
abstract class RegisterModule {
  @preResolve
  Future<GoogleSignIn> get googleSignIn async {
    final instance = GoogleSignIn.instance;
    await GoogleSignIn.instance.initialize();
    return instance;
  }

  @lazySingleton
  FirebaseAuth get firebaseAuth => FirebaseAuth.instance;

  @lazySingleton
  FirebaseFirestore get firestore => FirebaseFirestore.instance;

  @lazySingleton
  FacebookAuth get facebookAuth => FacebookAuth.instance;
}
```

`AuthRepositoryImpl` then takes all five collaborators as constructor parameters. Calling `FirebaseAuth.instance` inside the repository instead would hide the dependency from the container and leave no seam for a fake in tests — `@preResolve` is only needed for the one SDK that requires async setup.

## 6. Resolution helpers

Defined in `packages/core/common/lib/di/module.dart`:

| Helper | Missing registration | Use when |
|---|---|---|
| `getIt<T>()` | **Throws** | T is guaranteed — core infra you always ship |
| `getItOrNull<T>()` | Returns `null` | T belongs to a feature that may be removed |
| `getAll<T>()` | **Throws** | Never, for optional contributions |
| `getAllOrEmpty<T>()` | Returns `const []` | Collecting multi-instance contributions |

```dart
Iterable<T> getAllOrEmpty<T extends Object>({...}) {
  if (!getIt.isRegistered<T>()) {
    return const [];
  }
  return getIt.getAll<T>(...);
}
```

This is what makes a feature removable. The shell collects routes, tabs and localisation delegates with `getAllOrEmpty`, and optional singletons with `getItOrNull` + a fallback:

```dart
final entry = getItOrNull<IAppEntryLocation>()?.path;
if (entry != null) return entry;
```

> [!NOTE]
> `getIt.enableRegisteringMultipleInstancesOfOneType()` is called in `configureDependencies()` — that is what allows several packages to each register their own `IFeatureRouteModule`.

## 7. Constructor injection only

> [!CAUTION]
> **Never call `getIt<T>()` inside business logic** — ViewModels, Repositories, UseCases. Hidden lookups make a class untestable (you cannot pass a fake) and hide its real dependencies.

```dart
// Correct — dependencies are visible and mockable
@injectable
class LoginUseCase extends BaseUseCase<UserEntity, LoginParams> {
  LoginUseCase(this._authRepository);
  final IAuthRepository _authRepository;
}
```

Service-locator calls are acceptable only at composition seams: route `build()` methods, widget-tree wiring, and the app shell's assembly code.

## 8. Adding a new package to DI

1. Create `lib/di/module.dart` with `@InjectableInit.microPackage()` (the module generator does this).
2. Annotate your classes.
3. Run `dart run build_runner build -d --workspace`.
4. Import the generated module in `app/lib/di/injection.dart` and add `ExternalModule(YourPackageModule)` to the **right group** (`_domainModules`, `_dataModules`, `_featureModules`, …).
5. Verify the order in `injection.config.dart`.

### `ignoreUnregisteredTypes`

When a module references a type registered elsewhere, list it in `ignoreUnregisteredTypes` and import it with a **relative** path from the package barrel (e.g. `import '../domain_auth.dart';`) to satisfy the `prefer_relative_imports` lint.

## 9. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `type X is not registered` at startup | Eager singleton depends on a later module | Switch to `@LazySingleton` (§4) |
| `getItOrNull<Supertype>()` returns null | GetIt does not resolve supertypes | Add a `@module` binding (§5) |
| Storage getter returns `null` despite data on disk | Owner is `@injectable`; cache empty | Use `@lazySingleton` + `@PostConstruct(preResolve: true)` (§2) |
| Only one contribution collected | Multi-registration disabled | `enableRegisteringMultipleInstancesOfOneType()` must run before `getIt.init` |
| Stale screen state after re-entry | Screen controller is a singleton | Switch to `@injectable` |
| `getAll<T>()` throws | No implementation registered | Use `getAllOrEmpty<T>()` |

## Checklist

- [ ] Screen controllers `@injectable`; global ones `@lazySingleton`
- [ ] Anything depending on domain/data/feature types is **lazy**
- [ ] Storage owners are singletons with `@PostConstruct(preResolve: true)`
- [ ] New module added to the correct group in `injection.dart`
- [ ] Order verified in generated `injection.config.dart`
- [ ] Optional cross-feature lookups use `getItOrNull` / `getAllOrEmpty`
- [ ] No `getIt<T>()` inside VMs, repositories or use cases
