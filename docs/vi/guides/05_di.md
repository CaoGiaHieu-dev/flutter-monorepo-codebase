# Dependency Injection

**File này trả lời:** tôi nên dùng annotation nào, module của tôi được đăng ký ở đâu, và vì sao app ném lỗi "not registered" lúc khởi động?

**Đọc xong bạn làm được:** đăng ký bất kỳ class nào với scope đúng, hiểu thứ tự khởi tạo module, tránh bẫy eager singleton, và viết lệnh tra cứu sống sót được khi một feature bị gỡ.

---

## 1. Mô hình: GetIt + Injectable, mỗi package một module

Mỗi package sở hữu một DI module tại `lib/di/module.dart`:

```dart
import 'package:injectable/injectable.dart';

@InjectableInit.microPackage()
void initMicroPackage() {}
```

`build_runner` biến nó thành `lib/di/module.module.dart`, phơi ra ví dụ `CoreStoragePackageModule`. App shell lắp tất cả lại trong `apps/mobile/lib/di/injection.dart`.

Bạn chỉ cần gắn annotation lên class, nó tự vào module của package đó — không bao giờ phải sửa file generated.

---

## 2. Chọn scope

| Annotation | Vòng đời | Dùng cho | Ví dụ thật |
|---|---|---|---|
| `@injectable` | Instance mới mỗi lần resolve | VM / BLoC gắn màn hình | `HomeProfileBloc` |
| `@lazySingleton` | Một instance, tạo khi resolve lần đầu | Controller toàn app, owner của storage | `AuthProvider`, `AuthLocalDataSource` |
| `@singleton` | Một instance, tạo **trong lúc** DI init | Service toàn app không trạng thái; navigator dạng `@Singleton(as: …)` | `AppRouter`, `AppBootStorage`, `AuthNavigatorImpl` |
| `@Injectable(as: I)` | Factory bind vào interface | Đóng góp không state, resolve khi cần | `AuthActionHandlerImpl`, mọi `IFeatureLocalization` |
| `@LazySingleton(as: I)` | Singleton bind vào interface | Repository, route module | `AuthRepositoryImpl`, `NetworkConfigImpl`, `HomeNavDestination` |
| `@module` + `@preResolve` | Khởi tạo bất đồng bộ / thư viện ngoài | Kiểu bạn không sở hữu | `SharedPreferences`, Drift database của chính package |

> [!CAUTION]
> **Tuyệt đối không đăng ký controller gắn màn hình là singleton.** GetIt giữ nó mãi mãi, nên màn hình rò rỉ bộ nhớ và state bị cũ. Xem [`03_state_management.md`](03_state_management.md) §4.

### `@PostConstruct(preResolve: true)`

Dành cho class cần setup bất đồng bộ trước khi ai đó dùng tới:

```dart
@lazySingleton
class AuthLocalDataSource {
  AuthLocalDataSource(this._storageManager);

  final StorageManager _storageManager;

  late final _token = StorageValue<String>(
    _storageManager.getStorage(StorageType.secure),
    AuthStorageKeys.TOKEN,
  );

  late final _authUser = StorageValue<Map<String, dynamic>>(
    _storageManager.getStorage(StorageType.secure),
    AuthStorageKeys.AUTH_USER,
  );

  @PostConstruct(preResolve: true)
  Future<void> initialize() async {
    await Future.wait([_token.readFromStorage(), _authUser.readFromStorage()]);
  }

  // … getter và setter trên _token / _authUser
}
```

`preResolve: true` khiến DI `await` phần setup ngay trong `configureDependencies()`, rồi đăng ký lại instance *đã resolve* thành singleton đồng bộ — nên `getIt<AuthLocalDataSource>()` về sau chạy đồng bộ bình thường.

> [!WARNING]
> **`@injectable` + `@PostConstruct` là SAI với owner của storage.** Factory trả instance mới mỗi lần resolve, mỗi cái có **cache trong RAM rỗng**, nên getter đồng bộ trả `null` dù dữ liệu vẫn nằm trên đĩa. Owner của storage bắt buộc phải là `@lazySingleton` hoặc `@singleton`.

## 3. Thứ tự khởi tạo module

Đây là phần hay gây lỗi nhất. Thứ tự được khai đúng một lần, trong `app_manifest.yaml` của từng app ở mục `di_groups`, rồi `composer sync` sinh nó vào `apps/<id>/lib/di/injection.dart`:

```dart
const _externalModulesBefore = [..._coreModules];
const _externalModulesAfter = [
    ..._notificationsModules,
    ..._shellModules,
    ..._uiModules,
    ..._domainModules,
    ..._dataModules,
    ..._featureModules,
    ..._otherModules,
];
```

Thứ tự kết quả:

| # | Nhóm | Nội dung |
|---|---|---|
| 1 | `_coreModules` (**before**) | common, network, storage, database, di |
| – | *phần đăng ký của chính app* | `lib/` của app — ở app mẫu chỉ có `FirebaseModule` (`apps/mobile/lib/firebase/firebase_module.dart`) |
| 2 | `_notificationsModules` | `core_notifications` — `PushNotificationService` |
| 3 | `_shellModules` | `platform_app_shell` — `AppRouter`, `AppProvider`, `DeeplinkProvider`, `AppBootStorage`, `ILanguageStorage`, `IThemeStorage`, `NetworkConfig`, `SslPinningConfig` |
| 4 | `_uiModules` | `CoreBaseUiPackageModule` |
| 5 | `_domainModules` | domain_core, rồi package domain của từng module |
| 6 | `_dataModules` | data_core, rồi package data của từng module |
| 7 | `_featureModules` | package feature của từng module |
| 8 | `_otherModules` | provider / bloc state management |

Injectable chạy phần đăng ký *của chính package* nằm giữa hai phase. App chỉ dùng chỗ đó cho thứ định danh nó — `FirebaseOptions` theo từng flavor; mọi thứ khác đều đến qua một nhóm. Có ba vị trí là cố ý và không được "dọn dẹp":

**(a) `shell` đứng trước `ui`.**
`ThemeProvider` và `LanguageProvider` trong `core_base_ui` inject `IThemeStorage` / `ILanguageStorage`, mà implementation nằm ở `platform_app_shell` (`platform/app_shell/lib/di/theme_storage_impl.dart`, `language_storage_impl.dart`). Đảo hai nhóm này là các provider sẽ resolve storage trước khi nó tồn tại.

**(b) Package mở database phải chạy sau mọi thứ đóng góp migration cho nó.**
Mở database là `@preResolve`, và chính việc mở là thứ chạy các bước `IDatabaseMigration` đã thu thập — nên mọi bước phải được đăng ký trước khi mở. Bên trong package sở hữu, `@Order(1)` trên hàm mở giải quyết việc đó (`modules/cache/data/lib/di/module.dart`): injectable đăng ký các mục của một package theo `@Order` tăng dần, nên các bước của chính package (order mặc định 0) được đăng ký trước. Nhưng `@Order` không vươn sang module khác. `data_cache` (module mẫu `cache`) mở `CacheDatabase` của nó khi nhóm `data` khởi tạo, nên một migration do package thuộc nhóm *sau* đóng góp — ví dụ một feature — đơn giản là chưa có mặt, và bị bỏ qua mà không báo lỗi. Database của riêng bạn cũng cần `@Order(1)` y như vậy trên hàm mở. Bản thân `core_database` không đăng ký gì (nó chỉ là cơ chế), nên nó nằm trong `core` được.

**(c) `notifications` không nằm trong `core`.**
`PushNotificationService` là `@singleton` eager inject `FirebaseOptions`, mà `FirebaseOptions` lại do chính app đăng ký, giữa hai phase — chúng gắn với một bundle ID, nên không package platform nào được sở hữu. Đặt ở `before` thì service sẽ resolve chúng trước khi chúng tồn tại và ném lỗi lúc khởi động. App nào không gửi push notification thì bỏ nhóm này, và cũng không cần `lib/firebase/`.

## 4. Bẫy eager singleton

> [!CAUTION]
> **`@Singleton` eager không được phụ thuộc type do module chạy sau đăng ký.** Instance được dựng *ngay trong lúc* đăng ký, nên dependency chưa được đăng ký sẽ ném
> `Object/factory with type X is not registered inside GetIt` — ngay lúc khởi động app, mọi lần chạy.
>
> **`flutter analyze` KHÔNG bắt được lỗi này.** Đây là lỗi thứ tự lúc chạy, không phải lỗi kiểu.

Ca thật: `ThemeStorageImpl` là một `@Singleton(as: IThemeStorage)` eager trong nhóm `shell`. Dependency duy nhất trong constructor của nó là `StorageManager`, do `core_storage` đăng ký ở nhóm 1 — đúng chiều. Nếu nó inject thêm, chẳng hạn, `AuthLocalDataSource` từ `data_auth` (nhóm 6), app sẽ hỏng lúc boot ở mọi lần mở. Cách sửa chỉ là một từ — đổi thành `@LazySingleton` — hoặc tốt hơn, đừng phụ thuộc vào module nào cả.

Đó chính là điều `NetworkConfigImpl` làm. Nó từng inject `AuthLocalDataSource` và `RefreshTokenUseCase`, và phải lazy đúng vì lý do này. Giờ nó chỉ nhận `ILanguageStorage` từ chính nhóm của mình và đọc phiên đăng nhập qua `IAuthSessionGateway` ngay lúc gọi:

```dart
@LazySingleton(as: NetworkConfig)
class NetworkConfigImpl implements NetworkConfig {
  NetworkConfigImpl(this._languageStorage);

  /// Null in a build that composes no auth module.
  IAuthSessionGateway? get _session => getItOrNull<IAuthSessionGateway>();
  // ...
}
```

**Cách kiểm chứng.** File generated `apps/mobile/lib/di/injection.config.dart` chỉ chứa thứ tự module (mỗi package một lệnh `…PackageModule().init(gh)`). Đăng ký theo từng type nằm trong file generated `lib/di/module.module.dart` của từng package: kiểm tra mọi `gh.singleton<...>(...)` ở đó (không có `lazy`) chỉ gọi `gh<Dep>()` cho type đã đăng ký phía trên nó trong cùng file, hoặc bởi một module có `init` chạy sớm hơn trong `injection.config.dart`.

Nguyên tắc nhanh: class nào phụ thuộc bất cứ thứ gì từ `domain_*`, `data_*` hay `feature_*` thì phải để **lazy**.

## 5. Dual registration — bind một instance cho hai interface

> [!WARNING]
> **GetIt resolve theo đúng type đã đăng ký. Nó KHÔNG đi ngược chuỗi supertype.**

`NetworkConfig implements SslPinningConfig`, nhưng vì `NetworkConfigImpl` chỉ đăng ký `as: NetworkConfig` nên `getItOrNull<SslPinningConfig>()` trả `null` — khiến `AppInitializer` **âm thầm bỏ qua** certificate pinning ở staging và production. Binding tường minh trong `platform/app_shell/lib/di/network_binding_module.dart` là thứ làm cả hai type resolve được:

```dart
@module
abstract class NetworkBindingModule {
  @lazySingleton
  SslPinningConfig bindSslPinningConfig(NetworkConfig config) => config;
}
```

Tham số khai kiểu `NetworkConfig`, nên phép upcast được compiler kiểm tra — không cần ép kiểu `as`. Cùng pattern đó dùng để đăng ký agnostic stream hai lần (`@singleton` cụ thể cho owner, binding interface cho consumer) — xem [`10_cross_feature.md`](10_cross_feature.md).

### Bind thư viện bên thứ ba

Cũng chính cơ chế `@module` là cách một kiểu bạn không sở hữu đi vào container. `platform/storage/lib/di/module.dart`:

```dart
@module
abstract class CoreStorageDiModule {
  @preResolve
  Future<SharedPreferences> getSharedPreferences() async {
    return SharedPreferences.getInstance();
  }
}
```

`@preResolve` là thứ bắt `configureDependencies()` **await** cái này trước khi trả về, nhờ đó mọi nơi phía sau nhận `SharedPreferences` như một tham số constructor bình thường chứ không phải `Future`. Chỉ dùng nó khi việc khởi tạo thật sự bất đồng bộ; còn lại một getter `@lazySingleton` là đủ.

`@module` cũng là nơi bạn dựng một client từ object của package khác. `modules/auth/data/lib/di/register_module.dart` biến `Dio` dùng chung thành Retrofit data source của module:

```dart
@module
abstract class RegisterModule {
  @lazySingleton
  AuthRemoteDataSource authRemoteDataSource(Dio dio) =>
      AuthRemoteDataSource(dio);
}
```

Gọi `SharedPreferences.getInstance()` hay tự dựng `Dio` ngay trong repository sẽ giấu dependency khỏi container và không chừa khe hở nào để test truyền fake vào. Đó là toàn bộ lý do chúng nằm trong `@module`.

## 6. Các helper resolve

Định nghĩa tại `platform/kernel/lib/src/di/service_locator.dart`, được `platform/common/lib/di/module.dart` re-export:

| Helper | Khi chưa đăng ký | Dùng khi |
|---|---|---|
| `getIt<T>()` | **Ném lỗi** | T chắc chắn có — hạ tầng core luôn đi kèm |
| `getItOrNull<T>()` | Trả `null` | T thuộc feature có thể bị gỡ |
| `getAll<T>()` | **Ném lỗi** | Không bao giờ, với đóng góp tuỳ chọn |
| `getAllOrEmpty<T>()` | Trả `const []` | Gom các đóng góp nhiều instance |

```dart
Iterable<T> getAllOrEmpty<T extends Object>({...}) {
  if (!getIt.isRegistered<T>()) {
    return const [];
  }
  return getIt.getAll<T>(...);
}
```

Đây chính là thứ khiến feature gỡ được. App shell gom route, tab và delegate đa ngôn ngữ bằng `getAllOrEmpty`, còn singleton tuỳ chọn thì `getItOrNull` + fallback:

```dart
final entry = getItOrNull<IAppEntryLocation>()?.path;
if (entry != null) return entry;
```

> [!NOTE]
> `getIt.enableRegisteringMultipleInstancesOfOneType()` được gọi trong `configureDependencies()`, trước `getIt.init` — đó là thứ cho phép nhiều package cùng đăng ký `IFeatureRouteModule` của riêng mình. Thiếu nó, lần đăng ký thứ hai sẽ ném lỗi lúc boot (§9).

## 7. Chỉ dùng constructor injection

> [!CAUTION]
> **Tuyệt đối không gọi `getIt<T>()` bên trong business logic** — ViewModel, Repository, UseCase. Tra cứu ngầm khiến class không test được (không truyền fake vào được) và che giấu dependency thật của nó.

```dart
// ĐÚNG — dependency hiện rõ và mock được
@injectable
class LoginUseCase extends BaseUseCase<UserEntity, LoginParams> {
  LoginUseCase(this._authRepository);
  final IAuthRepository _authRepository;
}
```

Chỉ chấp nhận gọi service locator ở các mối nối lắp ráp: `build()` của route, chỗ nối cây widget, và code lắp ráp của app shell.

## 8. Thêm package mới vào DI

1. Tạo `lib/di/module.dart` với `@InjectableInit.microPackage()` (module generator làm sẵn).
2. Gắn annotation cho các class của bạn.
3. Chạy `dart run build_runner build --workspace`.
4. Thêm nó vào `app_manifest.yaml` của app — một module ở mục `modules:`, hoặc một package platform ở đúng mục `di_groups` — rồi chạy `dart tools/composer/composer.dart sync`. **Không bao giờ sửa tay `injection.dart`**: danh sách module của nó nằm giữa các marker `composer:managed`, và CI Gate 0 fail khi bị lệch.
5. Kiểm tra lại thứ tự: thứ tự module trong `injection.config.dart`, còn đăng ký của type và các lệnh `gh<Dep>()` của nó trong `lib/di/module.module.dart` của package.

### `ignoreUnregisteredTypesInPackages`

Không module nào cần tham số cho `@InjectableInit.microPackage()`, trừ `core_notifications` truyền `ignoreUnregisteredTypesInPackages: ['firebase_core']`: `FirebaseOptions` mà nó inject do `lib/firebase/firebase_module.dart` của từng app đăng ký, không bao giờ do một module của package. Đừng thêm tham số này để che một đăng ký thực sự bị thiếu.

## 9. Xử lý sự cố

| Triệu chứng | Nguyên nhân | Cách sửa |
|---|---|---|
| `type X is not registered` lúc khởi động | Eager singleton phụ thuộc module chạy sau | Chuyển sang `@LazySingleton` (§4) |
| `getItOrNull<Supertype>()` trả null | GetIt không resolve theo supertype | Thêm binding `@module` (§5) |
| Getter storage trả `null` dù đĩa có dữ liệu | Owner là `@injectable`; cache rỗng | Dùng `@lazySingleton` + `@PostConstruct(preResolve: true)` (§2) |
| Boot ném `ArgumentError: Type IFeatureRouteModule is already registered inside GetIt.` (hoặc `INavDestinationModule`, `IFeatureLocalization`, `IAppTreeWrapper` — bất kỳ kiểu nào mà nhiều package cùng đóng góp) | Chưa bật đăng ký nhiều instance. GetIt 9 không bao giờ âm thầm giữ lại một cái: lần đăng ký **không tên** thứ hai của một kiểu sẽ ném lỗi trừ khi `allowRegisterMultipleImplementationsOfoneType` được bật | `getIt.enableRegisteringMultipleInstancesOfOneType()` phải chạy trong `configureDependencies()` của app (`apps/<id>/lib/di/injection.dart`, viết tay, nằm ngoài các marker `composer:managed`) **trước** `getIt.init`. Test nào đăng ký hai instance cùng kiểu cũng phải gọi nó (`modules/dashboard/feature/test/dashboard_page_test.dart`) |
| State màn hình cũ khi vào lại | Controller màn hình là singleton | Chuyển sang `@injectable` |
| `getAll<T>()` ném lỗi | Chưa có implementation nào đăng ký | Dùng `getAllOrEmpty<T>()` |

## Checklist

- [ ] Controller màn hình `@injectable`; controller toàn cục `@lazySingleton`
- [ ] Bất cứ thứ gì phụ thuộc type domain/data/feature đều để **lazy**
- [ ] Owner của storage là singleton kèm `@PostConstruct(preResolve: true)`
- [ ] Package mới được ghép trong mỗi `app_manifest.yaml` — module ở mục `modules:`, package platform ở đúng mục `di_groups` — rồi `composer sync`
- [ ] Đã kiểm tra thứ tự: thứ tự module trong `injection.config.dart` generated, đăng ký theo type trong `lib/di/module.module.dart` của package
- [ ] Tra cứu xuyên feature tuỳ chọn dùng `getItOrNull` / `getAllOrEmpty`
- [ ] Không có `getIt<T>()` trong VM, repository hay use case
